## 0. 확정 방침 (대표, 2026-07-24) — 전 묶음 공통 제약

| # | 방침 | 로드맵에 미치는 영향 |
|---|---|---|
| P-1 | **디자인 B안(부티크 트래블) 고정, additive** | 모든 MVP는 기존 프론트 위에 화면/컴포넌트를 얹는다. 새 디자인 언어를 만들지 않는다 |
| P-2 | **무료 API 한도 안에서만** — Tmap 무료 1,000건/일, 공공데이터 개발계정 1,000회/일 | 읽기 경로에서 외부 API를 요청마다 때리지 않는다. 스팟/경로 데이터는 **배치/캐시**로 확보(00-impl-plan §3 원칙 승계) |
| P-3 | **법률 보류** — 실사용자 공개 전까지 개인정보처리방침·위치정보 신고 안 함 | 08 J8의 동의·고지 UI는 **자리만 확보(비활성/미노출)**하고 실제 동의 게이트를 강제하지 않는다. 단 로컬 LLM 채택으로 국외이전 이슈 자체가 소멸(아래 P-4) |
| P-4 | **M1 온보딩 = 로컬 LLM 확정** — Ollama `gemma4:12b`, `http://localhost:11434/api/chat`, `format:json`, temp 낮게. API 키·비용·국외이전 없음 | **LLM 호출은 backend가 Provider 인터페이스 뒤에서 감싼다.** 프론트는 Ollama를 직접 부르지 않는다(CORS·보안). CPU라 ~24초 → **로딩 UX 필수**. 상용 시 클라우드 구현체로 교체 가능 |

> **P-3 보충**: 법률 보류는 "지금 신고/방침 문서를 만들지 않는다"는 뜻이지, 개인정보를 함부로 수집한다는 뜻이 아니다. 08 정본의 최소수집 설계(민감 태그 세션 한정, `raw_input` 미저장 등)는 그대로 유지한다 — 공개 전환 시 법률 재검토 비용을 줄이기 위함.

## 2. 남은 기능의 의존성 그래프 (요약)

```
[완료] M2 혼잡도 ──┐
                  │
   M1 온보딩(태그) ─┼──▶ M5 로컬 스팟(추천화면) ──▶ M3 AI 경로 비교 ──┬──▶ M4 지도 + M15 히트맵
   (MVP-3)          │      (MVP-4)                   (MVP-5)         │      (MVP-6)
                    │                                                │
                    └────────────────────────────────────────────  └──▶ M6 로드밸런싱 + M14 날씨 + 저장코스/팁
                                                                           (MVP-7)

[독립·선택]  M11 두루누비 · M12 축제 · M9 오디오 · M8 사진인증 · M13 해시태그 문서  (MVP-8+, 착수 미확정)
```

- **화살표 = "먼저 있어야 함"** (우선순위 아님). 온보딩 태그가 없으면 추천/경로의 개인화가 성립하지 않고, 경로가 없으면 지도에 그릴 선이 없다.
- 각 묶음은 **혼자서도 로컬에서 돌아가 눈에 보이는** walking-skeleton 단위로 잘랐다(00-impl-plan 원칙 유지).

## 3. 구현 순서 (MVP-3 ~ N)

> 각 묶음의 "로컬에서 보이는 것"이 완료 판정(DoD)이다. 착수 직전에 해당 묶음의 상세 인터페이스 계약을 `01-interface-contract.md`에 부록(C, D, …)으로 additive 확정한다. **지금 전부 계약하지 않는다 — MVP-3만 부록 B로 못박았다.**

### MVP-3 — 온보딩(M1): 로컬 LLM 취향 추출 ★ 다음 착수분

- **한 줄**: 자연어 + 키워드 칩으로 취향을 입력하면, backend가 로컬 Ollama를 감싸 호출해 **취향 태그 JSON**을 추출하고, 온보딩 화면이 그 태그를 눈에 보이게 렌더한다.
- **의존**: 없음(독립 시작점). 출력(태그)은 MVP-4/5의 개인화 입력이 된다.
- **부서 분담**:
  - **backend** — `POST /api/v1/onboarding/analyze`(Ollama Provider 래핑 + 룰 폴백 + **서버가 tag_vector/scoring_weights 조립**), `GET /api/v1/onboarding/tag-schema`(칩 UI 소스). Ollama 직접 노출 금지.
  - **AI** — `LLMProvider` 인터페이스 + `OllamaProvider` 구현(시스템 프롬프트=08 §1.4 registry 영문코드, `format:json`, temp 낮게) + 룰 폴백(칩→태그 매핑, 08 A6) + 프롬프트 인젝션 방어(08 §5.5 — 이 호출이 방어 설계의 대상).
  - **frontend** — B안 온보딩 화면(자유 textarea + 칩), **~24초 로딩 UX**(진행 표시·중복제출 차단), 추출 태그 축별 렌더, 결과를 sessionStorage에 보관(서버 프로필 저장은 소비처 등장 시 도입).
- **계약**: **`01-interface-contract.md` 부록 B** (본 로드맵과 함께 확정).
- **로컬에서 보이는 것(DoD)**: 온보딩 화면에서 "6세 아이랑 반려견이 걷기 편한 곳" 입력 → 로딩 후 `가족/아이 동반/반려동물/도보/한적함/주차 필요…` 태그가 화면에 뜬다. Ollama가 꺼져 있어도 칩 기반 룰 폴백으로 화면이 죽지 않는다(`fallback_used:true`).

### MVP-4 — 로컬 스팟(M5) + 프로필 맞춤 추천 화면 ★ 다음 착수분 (계약: 부록 C 확정)

- **한 줄**: 공공 관광 API로 지역별 관광지·음식점·공방 데이터를 확보해 **추천 목록 화면**에 카드로 뿌리고, MVP-3 온보딩 프로필(sessionStorage)을 백엔드가 실소비해 적합도(`match_score`)로 정렬·표시한다.
- **의존**: M2(지역·혼잡도, 완료), M1(개인화 정렬 — 없어도 비개인화 기본 목록 성립, 있으면 personalized). 이게 M5 경로의 "재료"이자 **온보딩 프로필의 첫 실소비처**.
- **스코프 재단(무엇을 넣고 뺐나 — 부록 C.0 정본)**:
  - **넣는다**: ① 지역별 로컬 스팟 **배치 수집→로컬 스토어**(SQLite/JSON 시드, 무료 1,000회/일 준수) ② **프로필 맞춤 추천 목록**(카드·`match_score`·`match_reasons`·혼잡도 배지 M2 재사용·카테고리 필터) ③ `region_code` 기반 조회.
  - **뺐다**: 핫플vs숨은길 **1:1 비교(M3 전체)→MVP-5** / **지도·경로선(M4)→MVP-6** / 좌표 기반 "내 근처"·정밀좌표 opt-in→이후 / 서버측 프로필 저장(A2)→소비 안정화 후(이번엔 프론트 sessionStorage를 body로 전송, 서버는 재검증만).
- **부서 분담**:
  - **backend** — `POST /api/v1/places/recommend`(body에 region_code + sessionStorage 프로필, 응답은 스코어링된 `SpotCard[]`). 공공 TourAPI(D8 지역기반관광정보/근처 음식점 등) **배치 수집→로컬 스토어**. **스팟 데이터 소스·원천 필드명은 실호출로 확정**(추측 금지, 부록 C.1). **프론트 프로필 재검증**(신뢰경계, 부록 C.4). 스팟 스코어링 결합·정렬·`match_reasons` 조립·`is_hidden_gem`.
  - **AI** — `spot_fit`(코사인: 사용자 `tag_vector` vs 스팟 태그벡터 슬라이스 14~28) + `matched_tags` + accessibility 하드필터 판정. **MVP-3 출력의 첫 실소비처.** 08 compare(D1)와 동일 소관 분리(AI는 fit만, backend가 나머지).
  - **frontend** — B안 추천 화면(신규 라우트). sessionStorage `sumeungil:onboarding-result:v1` **없으면 온보딩 유도**, 있으면 body로 전송. 스팟 카드·카테고리 필터·`match_reasons` 변환 표시·`themes.barrier_free:null`=회색·enum/수치 재판정 금지.
- **계약**: **`01-interface-contract.md` 부록 C**(본 상세화와 함께 확정).
- **인프라**: 로컬 스토어(스팟) 이번에 첫 실도입 — SQLite/JSON 시드로 시작(§4).
- **로컬에서 보이는 것(DoD)**: 지역 선택 시 실제 관광지/음식점 카드가 뜨고, 온보딩을 마친 사용자는 카드에 `match_score`와 "반려동물 동반 가능·혼잡도 낮음" 같은 적합 근거가 붙어 상위 정렬된다. 프로필이 없으면 비개인화 목록(혼잡도 낮은 순) + 온보딩 유도.

### MVP-5 — AI 경로 비교(M3): 핫플 vs 숨은길 1:1 대조 리포트 ★ 계약 확정(부록 D) — 다음 착수분

- **한 줄**: 지정과제(오버투어리즘)의 답을 **"붐비는 유명 핫플" vs "AI가 찾은 한적한 숨은길"**을 나란히 대조하는 **1:1 리포트(카드/표)**로 산출한다. **이미 만든 조각(M2 혼잡도·M4 추천·M3 프로필)을 조립**한다 — 새 공공 API·데이터셋을 만들지 않는다. **프로젝트의 얼굴이자 공모전 창의성 축의 핵심.**
- **의존**: M1(태그, MVP-3 완료)·M5(스팟, MVP-4 완료)·M2(혼잡도, 완료) 전부 필요 → 세 조각이 이미 있으므로 **바로 착수 가능**.
- **스코프 재단(무엇을 넣고 뺐나 — 부록 D.0 정본)**:
  - **넣는다**: ① 핫플 vs 숨은길 **대칭 카드 2개 + 지표별 델타 + verdict headline** ② 비교 축 **2개(혼잡도 붐빔↔여유, 프로필 적합도 일률↔맞춤)** + tier(신뢰도) 부속 배지 ③ `POST /api/v1/compare`(region+프로필→hotspot/hidden 대칭 응답).
  - **뺐다**: **지도·경로선(Tmap 렌더)→MVP-6** / **이동거리·시간 축**(경로·좌표 없음 → 지어내지 않음)→MVP-6 / **방문 신뢰도(리뷰) 축**(리뷰 미수집)→이후 / **로드밸런싱**(M6)→MVP-7 / 비교결과 영속·`GET /compare/{id}`·LLM headline→도입 안 함.
- **부서 분담**:
  - **backend** — `POST /api/v1/compare`. 핫플 선정(**M2 board rank1 재사용** + 이름매칭 시 스토어 enrich, 부록 D.1.1), 숨은길 선정(**recommend 파이프라인 재사용**, D.1.2), `deltas`(congestion_diff/pct·fit_diff) 계산, `build_verdict()` **템플릿 조립(LLM 아님, 수치·enum·개수만 삽입 → 인젝션 표면 0, 부록 D.4.1)**, CompareSpot 대칭 봉투. 프로필 재검증은 **부록 C.4 함수 그대로 재사용**.
  - **AI** — **이번 신규 작업 없음.** `spot_fit.cosine_spot_fit`/`matched_tags`(MVP-4 산출물)를 핫플·숨은길 양쪽에 재사용할 뿐. 08 §3 `score_routes`(경로 스코어링)는 좌표·경로가 생기는 MVP-6~7로 이연.
  - **frontend** — B안 비교 화면(신규 라우트). 추천 화면에서 스팟 탭 시 진입(`hidden_id` 전달). **모바일=상단 요약 스코어카드 + 지표별 행 스택**(08 designer 해법 재사용), **1024px↑=2컬럼 대칭 카드**. 거리·리뷰 행 미표기, headline 텍스트 노드 렌더, enum·수치 재판정 금지(부록 D.7).
- **계약**: **`01-interface-contract.md` 부록 D**(본 상세화와 함께 확정). 34필드 설계 정본(`sumeungil/08` §2)을 핵심 2축 + 대칭 카드로 재단.
- **로컬에서 보이는 것(DoD)**: 추천 화면에서 숨은 스팟을 고르면 비교 화면으로 진입해, 좌/우(모바일 상/하) 대칭 카드로 **"핫플 A(혼잡 82p) vs 숨은길 B(여유·맞춤 3개 충족)"**가 뜨고, 상단 headline("붐비는 유명 스팟 대신 혼잡도 71% 낮은 한적한 곳, 맞춤 조건 3개 충족")이 **수치 기반으로 조립**된다. 지도·경로선은 없다(MVP-6).

### MVP-6 — 지도 시각화(M4) + 혼잡도 히트맵(M15)

- **한 줄**: MVP-5의 경로를 **Tmap JS SDK** 지도에 선·마커로 그리고, M2 예측 혼잡도를 지도 위 색상 오버레이로 얹는다.
- **의존**: M3(그릴 경로)·M2(오버레이 데이터). Tmap JS SDK + (선택) Tmap Route API(M10)로 실제 경로 스냅.
- **부서 분담**:
  - **backend** — (M10) Tmap Route 프록시로 `path_source:"snapped"` 좌표열 확보 → **결과 캐시**(무료 1,000건/일 제약). 히트맵 데이터는 D1(전광판) 재사용, 새 데이터셋 불필요.
  - **frontend** — Tmap SDK 로드, polyline/마커, 혼잡도 GroundOverlay/색상 오버레이. B안 팔레트로 렌더.
  - **AI** — 없음(스코어링·08 정본과 무관, 순수 시각화 증분).
- **계약**: 착수 직전 부록 E. **확인 필요**: Tmap JS SDK 키 도메인/localhost 허용·무료 쿼터 소진 시 폴백을 backend가 실확인.
- **로컬에서 보이는 것(DoD)**: 비교 화면에서 경로가 지도에 실제 선으로 그려지고, 지도 위에 혼잡 지역이 색으로 보인다.

### MVP-7 — 동적 로드밸런싱(M6) + 날씨 재정렬(M14) + 저장코스/여행팁 화면

- **한 줄**: M3 스코어링 결과 위에 **분산(로드밸런싱)·날씨 보정 재정렬**을 얹고, 사용자가 코스를 저장·조회하는 화면을 붙인다.
- **의존**: M3(그 위에 얹는 rerank 레이어). 저장은 경로 존재 전제. 08 §3의 "페널티는 선택 레이어 단 1회" 원칙 준수.
- **부서 분담**:
  - **backend** — `select_route_with_balancing()`(08 §3), 날씨(D18 기상청) rerank 레이어(08 M14 방식: 스코어 산출 이후 재정렬), 저장코스 스토어(여기서 **영속 저장소가 처음 실필요** → 인터페이스 뒤에서 도입).
  - **AI** — capacity 미확보 코스용 **2순위 상대 share 지표**(08 §3.4).
  - **frontend** — 분산 안내 배너(이미 목업에 상태 설계됨, 08 G6), 저장코스·여행팁 화면.
- **계약**: **`01-interface-contract.md` 부록 F**(2026-07-24 확정). 아래 파트별 실행 세부.

#### MVP-7 실행 세부 (부록 F 확정 — 파트별 분담·검수 등급)

> **근본 재단**: MVP-5/6이 스팟 단위(route 경로탐색·서버 카운터 없음)이므로 08 §3 **경로 기반** 로드밸런싱(`weighted_count`/capacity/dedupe 카운터)은 MVP-7 build에서 성립 불가 → **공공데이터 `congestion.index`를 혼잡 신호로 스팟 목록을 재정렬**한다. 08 불변식 "**페널티는 선택 레이어 단 1회**"는 보존(스코어링 순수, rerank에서만 조정). route 단위 LB·서버 영속저장소·격자매핑은 상용 이연.

| 파트 | backend | AI | frontend | 검수 등급 제안 |
|---|---|---|---|---|
| **1. 로드밸런싱(M6)** | `recommend` 응답에 `rerank.distribution` **additive 확장**(새 엔드포인트 0), `apply_balance_rerank()` — match_score 불변·순서만 1회 조정(부록 F.1-4) | 없음(스코어링 재사용) | `rerank:{balance:true}` 요청, 분산 배너(08 G6 상태 재사용), 서버 순서 그대로 렌더 | **약식~풀 판단** → rerank가 스코어링에 새어들면(순환·이중적용) 08 핵심 위반이라 **QA 필수**. 개인정보·시크릿 신규 없음 → **약식(QA 단독)**, 단 "페널티 단1회" 회귀 시 풀 승격 |
| **2. 저장코스** | **없음**(서버 엔드포인트 0) | 없음 | localStorage `sumeungil:saved-spots:v1` upsert/조회, `/saved` 화면, 스냅샷+`saved_at` 정직표기(부록 F.2) | **생략~약식** → 순수 프론트 localStorage 1화면. 오케스트레이터 직접검증 가능 수준이면 **생략**, 묶음까지 구현 시 **약식** |
| **3. 여행팁** | 없음 | 없음 | 정적 JSON `/tips` 화면(부록 F.3). 문구는 **content-marketer 후속**(과대광고·법률 리스크 금지 톤) | **생략**(정적 콘텐츠·코드 비변경 수준). 문구 작성 후 content-marketer 자체 톤 검토 |
| **4. 날씨(M14)** | `WeatherProvider`(구현체 실호출 확정, Null 폴백), `rerank.weather` 블록, `apply_weather_rerank()` — 파트1 결과 안에서만 1회(부록 F.4) | 없음(카테고리 판별=결정론) | `rerank:{weather:true}`, "준비중" 정직 배지/실내 우선 배너 | **약식** → Provider 뒤 graceful·외부문자열 미삽입. 신규 외부 데이터 연동이나 개인정보 아님 → **QA 단독**, 시크릿(PUBLIC_DATA_API_KEY) 하드코딩 확인 |

- **착수 순서 제안**: 파트2·3(프론트 단독, backend 무관)은 병렬 즉시 착수 가능. 파트1은 recommend 확장이라 backend+frontend 병렬. 파트4는 파트1 rerank 레이어 위에 얹으므로 **파트1 다음**(결합 순서 부록 F.4-4: 혼잡 필터 먼저, 날씨는 그 안에서).
- **CEO 액션(부록 F.4-8, 아래 §7)**: 날씨는 대표 미승인이어도 `NullWeatherProvider`로 graceful 진행 — MVP-7을 막지 않는다.

- **로컬에서 보이는 것(DoD)**: 혼잡 임계 초과 시 "붐비는 곳 대신 이 대안" 분산 배너가 실제로 뜨고(대안 없으면 "전반적 붐빔" 정직 안내), 저장한 스팟이 `/saved`에서 오프라인에서도 유지되며, 여행팁 화면이 카테고리별로 렌더되고, 날씨 데이터가 있으면 비 예보 시 실내 스팟이 위로 재정렬(없으면 "날씨 정보 준비중" 정직표기 + 추천은 정상).

## 4. 인프라 도입 시점 (00-impl-plan §3 승계)

MVP-1의 "Redis·DB 없이 인터페이스만" 원칙을 유지하되, 실필요가 생기는 지점에서 인터페이스 뒤로 도입한다:

| 자원 | 처음 실필요 지점 | 근거 |
|---|---|---|
| 로컬 스토어(스팟 데이터) | MVP-4 | 공공 API 무료 한도 → 배치 수집분을 로컬에 보관. SQLite/JSON 시드로 시작, 상용 시 PostGIS |
| 영속 저장소(사용자 저장코스) | MVP-7 | 저장 기능이 처음으로 서버 영속을 요구 |
| Redis(게스트 프로필/캐시) | MVP-4~5 소비처 등장 시 | 온보딩 태그를 서버가 보관해야 하는 순간. 그 전(MVP-3)은 클라이언트 sessionStorage |

**LLM 인프라는 MVP-3에서 유일하게 로컬 Ollama를 실사용**한다. 다른 MVP는 LLM을 쓰지 않는다(경로 랭킹·verdict는 결정론 규칙/템플릿 — 08 §5 정본).
