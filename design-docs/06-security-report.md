## 판정

# **Critical 0건 / High 7건 / Medium 10건 / Low 8건**

### 3차 게이트 판정: **통과 (조건부 승인)**

- **Critical 0건** → CLAUDE.md 3차 게이트 통과 조건 충족.
- 단, **High 7건은 "설계 단계에서 잡지 않으면 나중에 못 잡는 것"에 해당**한다. 구현 착수(후속 프로젝트) 전에 설계 문서에 반영되어야 하며, 반영 없이 코드 작성이 시작되면 그 시점에 Critical로 격상된다.
- 대표 최종 결재를 막을 사유는 없다. **"설계 묶음 승인 + High 7건 반영 조건"**으로 결재 요청하는 것이 적절하다.

### 왜 Critical이 0건인가 (판정 근거)

Critical은 "배포 시 즉시 대량 개인정보 유출 또는 인증 전면 우회"로 한정했다. 현재:
- 실행 코드가 없어 실제 익스플로잇 가능한 표면이 존재하지 않는다.
- 최대 위험 항목(raw_input 보관, 게스트 승격)은 **backend와 legal이 이미 자진 인지·표기**한 상태여서 "미인지 결함"이 아니다.
- 인증 설계의 핵심(토큰 저장 위치, rotation, `/me/*` 구조)은 오히려 **설계가 양호**하다(8절 참조).

> 표기 규칙: 법률팀이 이미 지적한 항목은 **"법률팀 L-N과 중복"**으로 표시하고 **보안 관점의 추가 의견만** 기술한다.

### 2.1 High (7건)

---

#### S-H1. `user_profiles.raw_input` 자유서술 원문의 무기한 저장 — 목적 없는 보관 + 민감정보 유입

- **심각도**: High
- **위치**: `01-backend-design.md` 5.2절 DDL `user_profiles.raw_input TEXT` (L211~212) / `02-ai-strategy.md` 1.4절 User Prompt
- **법률팀 L-2, L-3과 중복** (제3자·아동 정보 유입, 원문 보관 기간)

**보안 관점 추가 의견 (법률팀이 다루지 않은 부분):**

1. **이 컬럼은 기능상 아무도 읽지 않는다.** 데이터 흐름은 `raw text → tags → weight_vector`이고, 스코어링(3.2절)·하드필터(3.1절)·랭킹은 전부 `tags`와 `weight_vector`만 소비한다. **`raw_input`을 SELECT 하는 쿼리가 설계 전체에 단 한 건도 없다.** 이용 목적이 문서에 명시되지 않은 채 저장만 되는 구조이며, 개인정보보호법의 **목적 명확화·최소수집 원칙 위반 소지**다.
2. **가장 위험한 데이터가 가장 통제가 약한 곳에 있다.** 자유 서술은 구조화 태그와 달리 무엇이 들어올지 통제할 수 없다 — "6세 아이"(아동 정보), "휠체어 타는 어머니"(제3자 건강·장애 = 민감정보), "성당 근처"(종교 추론), "재활 치료 끝나고"(건강). enum으로 강제되는 `tags`와 달리 여기엔 어떤 스키마 방어도 걸리지 않는다.
3. **법률팀 조치안("가급적 적지 마세요" 가이드 문구)은 기술적 통제가 아니다.** 안내 문구는 사용자의 자발적 협조에 의존하며, 자유 서술을 유도하는 UX(온보딩의 핵심 차별점)와 정면 충돌한다. 문구를 넣어도 사용자는 여전히 "6세 아이랑 반려견"이라고 쓴다 — 그게 이 서비스가 요구하는 입력이기 때문이다.

**사고 시나리오**: 외부 침해가 아니라 **누적형 사고**다. 1년간 raw_input이 쌓인 뒤 DB 유출 또는 내부자 조회가 발생하면, 유출되는 것은 "취향 태그"가 아니라 **"누가 몇 살 아이를 키우고, 가족 중 누가 휠체어를 쓰는지"**의 원문 텍스트 집합이다. 태그만 저장했을 때와 피해 규모가 질적으로 다르다.

**완화책 (우선순위 순)**
1. **기본은 미저장.** `raw_input` 컬럼을 DDL에서 제거하고 태그 추출 후 원문은 메모리에서 폐기한다. 설계 단계에서만 가능한 조치다.
2. 재추출(`vector_version` 변경 시) 목적으로 보관이 꼭 필요하다면: (a) 목적을 문서에 명시, (b) `raw_input_expires_at TIMESTAMPTZ NOT NULL DEFAULT now() + interval '30 days'` + 일 1회 파기 배치, (c) 컬럼 레벨 암호화(pgcrypto 또는 앱 레벨), (d) 개인정보처리방침에 보유기간 명시.
3. 저장 전 서버에서 **PII 정규식 스크러빙**(전화번호·이메일·주민번호 패턴 마스킹) — S-M4와 동일 모듈 재사용.
- **담당 부서**: backend-engineer (DDL·파기 배치), planning-lead (보관 여부 정책 결정), legal-counsel (보유기간 확정)

#### S-H2. 정밀 좌표를 URL 쿼리스트링으로 전송 — "비저장·비로깅" 설계 주장이 성립하지 않음

- **심각도**: High
- **위치**: `01-backend-design.md` 3절 위치 정밀도 표(L111) / 6.2절 C1 `GET /api/v1/places?...&near=35.1587,129.1604` (L618~619) / 10.5절 `middleware/request_log.py` (L1205)

**PRD가 명시적으로 물은 항목("이 설계가 실제로 안전한가")에 대한 답: 정책 방향은 옳지만, 전송 방식이 정책을 무효화한다.**

문서 3절은 정밀 좌표에 대해 *"저장하지 않음. 요청 파라미터로만 받고 응답 후 폐기, **로그에도 미기록**"*이라고 단언한다. 그러나 이를 강제하는 수단으로 제시된 것은 애플리케이션 미들웨어(`request_log.py`의 "정밀좌표 미로깅") **하나뿐**이다. 좌표가 URL 쿼리스트링에 실리면 애플리케이션이 통제할 수 없는 여러 계층에 잔류한다.

| 잔류 지점 | 근거 | 앱 미들웨어가 막을 수 있는가 |
|---|---|---|
| **Nginx access log** | 2.1절 구성도에 Nginx가 TLS 종단·리버스프록시로 존재. 기본 `combined` 포맷의 `$request`는 **쿼리스트링을 포함한 URI 전체**를 기록한다 | 불가 — 앱보다 앞단 |
| 브라우저 히스토리 / 세션 복원 | GET URL | 불가 |
| `Referer` 헤더 (지도 SDK 등 외부 도메인 요청 시 전송) | GET URL | 불가 |
| CDN·클라우드 LB 액세스 로그 | 배포 구성 미명시 | 불가 |
| APM/에러 트래커 요청 URL | 도입 여부 미명시 | 불가 |

**사고 시나리오**: 침해가 필요 없다. 정상 운영만으로 서버 디스크의 Nginx 로그에 `guest_id` 쿠키 값과 GPS 좌표(소수점 4자리 = 약 11m)가 **같은 로그 라인에** 축적된다. 이는 특정 개인(식별자)과 결합된 위치정보 = **개인위치정보**이며, "수집·보관하지 않는다"는 3절 설계 결론(및 이를 근거로 낮게 평가된 R4 리스크)이 사실과 달라진다. 법률팀 L-1 판정(위치기반서비스사업자 신고 대상 여부)의 **전제 자체가 흔들린다.**

**비대칭 지적**: 같은 좌표를 `POST /routes/compare`(D1)는 **request body**로 받는다. 즉 설계 안에 이미 안전한 방식이 존재하는데 C1만 쿼리스트링이다. 일관성 결함이다.

**완화책**
1. **정밀 좌표를 GET 쿼리스트링으로 받지 않는다.** C1을 `POST /api/v1/places/search`(body 수신)로 바꾸거나 좌표만 body로 분리.
2. 좌표를 그대로 보내지 않는다 — **클라이언트에서 소수점 3자리 반올림**(약 110m 격자). "내 근처 정렬" 용도에 충분하며 로그 잔류 위험도 함께 낮아진다.
3. Nginx `log_format`에서 쿼리스트링 제외(`$uri`만) 또는 `map`으로 좌표 파라미터 마스킹. **이 요구사항을 3절에 명문화**한다 — 현재 앱 미들웨어만 언급하고 있어 구현자가 Nginx 설정을 놓친다.
4. 3절 표의 "로그에도 미기록"에 **"앱·웹서버·프록시 전 계층에서"**를 명시하고 강제 수단을 각각 적는다.
- **담당 부서**: backend-engineer (API 시그니처·Nginx 설정 명세), designer (좌표 반올림), legal-counsel (L-1 재판정 시 반영)

#### S-H3. `cmp:{hash(req)}` 캐시가 개인화 결과를 사용자 간 교차 서빙

- **심각도**: High (구현 시 Critical)
- **위치**: `01-backend-design.md` 9.1절 Redis 키 표 `cmp:{hash(req)}` (L1095) × 6.2절 D1 Request 스키마 `"profile": {"use_saved": true}` (L650)

**두 문서 조각을 교차하면 결함이 드러난다.**

D1 `POST /routes/compare`의 request body는 `{"origin", "destination", "profile": {"use_saved": true}, "transport_mode", "departure_at"}` 이다. `use_saved = true`인 경우 **body에 사용자를 구분하는 정보가 하나도 없다.** 사용자 A와 B가 같은 목적지·교통수단·출발시각으로 요청하면 `hash(req)`가 **동일**하다. 그런데 응답에는 개인화 산출물이 들어 있다:
- `spot_fit.score` / `matched_tags` / `unmatched_tags` — A의 온보딩 태그로 계산된 값
- `match_reasons` — "반려동물 동반 가능", "주차 여유" 등 **A의 프로필을 역추론할 수 있는 문자열**
- `verdict.headline` — "…반려동물 동반 조건을 모두 만족합니다"

**시나리오 (정찰용 최소 기술)**: 인기 목적지에 대해 표준 파라미터로 반복 요청하면 직전에 같은 조합으로 요청한 타 사용자의 캐시된 개인화 결과를 수신한다. 여기서 **타인이 반려동물을 동반하는지, 유모차/휠체어가 필요한지(= 육아·장애 정보)** 를 유추할 수 있다. 능동 공격 없이 **정상 요청만으로** 발생하며, 반대 방향으로는 추천 품질 저하도 동반한다.

**부분 인지 상태**: 9.2절 3원칙 ③은 *"compare 결과 캐시 키에 로드밸런싱 결과를 포함하지 않는다… `cmp:*`는 혼잡도·후보집합까지만 캐시하고 최종 route 선택은 매 요청 수행"*이라고 적어 **로드밸런싱 무력화 문제는 인지**했다. 그러나 **개인화 필드가 캐시 대상인지 여부는 명시되지 않았다.** "혼잡도·후보집합까지만"이라면 안전하나, 그렇다면 9.1절의 키 이름 `cmp:{hash(req)}`(= compare 응답 캐시로 읽힘)와 모순된다. **설계 내부 불일치이며, 구현자가 9.1절만 보고 구현하면 사고가 난다.**

**완화책**
1. **캐시 키에 프로필 신원을 반드시 포함**: `cmp:{subject_hash}:{hash(req)}`, `subject_hash = HMAC(server_key, user_id 또는 guest_id)`. 또는 `hash(weight_vector + vector_version)`을 포함(같은 취향끼리 공유은 무해하므로 캐시 효율도 유지 — 권장).
2. 9.1절 키 표의 `cmp:*` 행에 **캐시 대상 화이트리스트** 명시: 캐시 가능 = 후보집합·혼잡도·경로 지오메트리 / 캐시 금지 = `spot_fit`, `match_reasons`, `verdict`, `load_balancing`.
3. 9.1/9.2절의 상충 서술을 한쪽으로 정리한다.
- **담당 부서**: backend-engineer

#### S-H4. 게스트 식별자 이중 경로(HttpOnly 쿠키 ↔ `X-Guest-Id` 헤더) — 설계 자기모순이 프로필 탈취 표면을 만든다

- **심각도**: High
- **위치**: `01-backend-design.md` 6.0절 *"게스트는 `X-Guest-Id` 헤더"* (L518) × 10.2절 *"guest_id | **HttpOnly 쿠키** | 24시간"* (L1170) × 10.1절 게스트 승격 흐름(L1152~1157)
- backend 자진신고(13절 QA 리스크 2번)에 대한 검증 결과

**PRD가 요구한 "실제 공격 시나리오"**

전제: 게스트 온보딩 프로필은 `session:guest:{guest_id}`(Redis, 24h)에 저장되며, 회원가입 시 **`user_profiles`로 승격 이관**된다(10.1절). 이 프로필에는 `raw_input`(아이 나이·장애 정보 포함 가능)과 `tags`가 들어 있다.

```
1. 공격자가 정상적으로 게스트 체험을 시작해 자신의 guest_id를 얻는다.
2. 공격자가 POST /api/v1/auth/signup 을 호출하되,
   요청에 X-Guest-Id: <피해자의 guest UUID> 를 지정한다.
3. 서버는 해당 헤더 값으로 session:guest:{피해자} 를 조회해
   신규 생성된 공격자 계정의 user_profiles 로 이관한다.
4. 공격자는 자기 계정에서 피해자의 온보딩 원문·태그를 열람한다.
```

**실현 가능성 평가 (과장하지 않음)**
- `guest_id`는 UUIDv4로 명시되어 있어(10.2절) **무작위 대입은 비현실적**(2^122). 따라서 이 시나리오는 **guest_id 유출을 선행 조건으로 한다.**
- 문제는 **설계가 그 선행 조건을 스스로 만든다**는 점이다. `X-Guest-Id`는 HTTP 요청 헤더이므로 프론트엔드 JavaScript가 값을 알고 직접 붙여야 한다. 그런데 10.2절은 같은 `guest_id`를 **HttpOnly 쿠키**(= JS가 읽을 수 없음)로 규정한다. **두 규정은 동시에 성립할 수 없다.**
- 구현자가 이 모순을 해소하는 가장 쉬운 방법은 **HttpOnly를 포기하고 `localStorage`나 일반 쿠키에 두는 것**이다. 그 순간 XSS(S-M7·S-M2 경로), 브라우저 확장, 공유 기기, 로그 노출을 통해 guest_id가 실제로 유출 가능해진다. 즉 **모순을 방치하면 구현 단계에서 자동으로 취약해진다** — 전형적인 "설계에서 안 잡으면 못 잡는" 항목이다.

**완화책 (설계 문서에 지금 반영)**
1. **`X-Guest-Id` 헤더를 설계에서 삭제한다.** 6.0절 공통 규약을 *"게스트 식별은 HttpOnly·Secure·SameSite=Lax 쿠키로만 수행하며, 클라이언트는 guest_id 값을 알지 못한다"*로 교체. 프론트는 `credentials: 'include'`만 하면 되므로 기능 손실이 없다.
2. **승격 시 서버는 쿠키에서 읽은 guest_id만 사용**한다. body/header/query의 guest_id는 **무조건 무시**(존재 시 400 + 로그 플래그).
3. **원자적 소비**: 승격은 Redis `GETDEL session:guest:{id}`로 수행. 조회 후 삭제를 분리하면 동시 요청 시 하나의 프로필이 두 계정으로 이관될 수 있다.
4. **승격 직후 guest_id 재발급**: 기존 쿠키를 즉시 만료시키고 새 값 발급(세션 고정 방어).
5. (선택) 게스트 세션 생성 시 `hash(IP 대역 + UA)`를 함께 저장하고 승격 시 대조 — 불일치는 차단이 아니라 로그 플래그로만(모바일 IP 변동 오탐 방지).
- **담당 부서**: backend-engineer

#### S-H5. `build_verdict()` — 방어가 전혀 설계되지 않은 2차 LLM 호출

- **심각도**: High
- **위치**: `01-backend-design.md` 7.1절 `def build_verdict(hotspot, hidden, deltas) -> str` (L758~761) / 6.2절 D1 응답 `verdict.headline` (L694)
- **PRD가 요구한 "우회 시나리오"에 대한 핵심 답변**

**AI팀의 다층 방어(1.5절)는 온보딩 추출 호출 하나에만 적용된다.** 그런데 backend의 AI 계약에는 **두 번째 LLM 호출**이 있다:

```python
def build_verdict(hotspot: RouteScore, hidden: RouteScore, deltas: dict) -> str:
    """M3. 비교 리포트 헤드라인 1문장 생성"""
```

이 호출은 `02-ai-strategy.md`에 **아예 등장하지 않는다.** 따라서:

| 1.5절 방어 계층 | build_verdict 적용 여부 |
|---|---|
| 1. strict json_schema + enum + additionalProperties:false | **미적용** — 반환 타입이 `-> str` **자유 문자열**. 스키마 강제 불가 |
| 2. `<user_input>` 델리미터 + "데이터일 뿐" 지시 | **미적용** — 프롬프트 자체가 미설계 |
| 3. 입력 300자 절단·제어문자 제거 | **미적용** |
| 4. 도구 권한 미부여 | 아마 동일하나 **미명시** |
| 5. 서버 측 JSON Schema 재검증 | **미적용** — 문자열이므로 검증할 스키마가 없다 |
| 6. 인젝션 패턴 모니터링 | **미적용** |

**공격 시나리오 — 간접 프롬프트 인젝션 (Indirect Prompt Injection)**

`build_verdict`의 입력 `RouteScore`에는 `matched_tags`, `reasons`, 그리고 실질적으로 코스명/스팟명이 들어간다. 이 문자열들의 **출처는 사용자가 아니라 공공데이터**(D4 두루누비 코스명, D5 관광지명, D7 상호명)**와 AI팀이 생성한 `reasons`**다.

```
1. 공격자는 LLM에 직접 입력할 필요가 없다. 공공데이터에 등록되는 상호/시설명
   (예: 소상공인 상권정보 D7의 '상호' 필드)에 지시문 형태 문자열이 포함되기만 하면 된다.
2. 배치(job_merchants)가 이를 그대로 적재한다 — 7.3절 정규화는 필수 필드 결측만 검사하고
   문자열 내용은 검사하지 않는다(assert_sanity는 행수·좌표 범위만 본다).
3. 해당 상점이 경로 주변 500m에 잡히면 build_verdict의 입력으로 들어간다.
4. 출력 headline은 자유 문자열이므로 공격자 통제 문자열이 그대로 실린다.
5. headline은 D1 응답 최상단 → AI 경로 비교 화면(서비스의 얼굴)에 크게 렌더링된다.
```

**영향 2가지**
- **저장형 XSS 경로**: LLM 출력 → 무검증 → 화면 렌더. 출력 인코딩 규정이 어느 문서에도 없다(S-M7과 동일 뿌리). React 기본 이스케이프가 있으면 완화되지만, **설계에 명시가 없으면 구현자가 `dangerouslySetInnerHTML`을 쓰지 않으리라는 보장이 없다.**
- **콘텐츠 무결성 훼손**: 심사 시연 화면의 핵심 문구가 외부 데이터로 조작될 수 있다. 공모전 맥락에서 실질 피해가 크다.

**완화책 (권장 순)**
1. **`build_verdict`를 LLM으로 구현하지 않는다.** 함수 시그니처가 스스로 말해준다 — `deltas`는 **backend가 이미 계산한 수치**다. 필요한 건 `f"{d}분 더 걸리지만 혼잡도는 {c}p 낮고, {조건}을 만족합니다."` 수준의 **템플릿 문자열 조립**이며 LLM이 필요 없다. 이 한 줄 결정으로 High 취약점 하나와 LLM 호출 비용·지연이 동시에 사라진다. **이것이 권고안이다.**
2. LLM을 유지한다면 최소 방어 명시: (a) 출력 길이 상한 120자, (b) 허용 문자셋 화이트리스트(`<`, `>`, `&`, 백틱 차단), (c) **수치 일치 검증** — headline의 숫자가 `deltas`와 불일치하면 폐기 후 템플릿 폴백, (d) 입력 문자열(코스명·상호명)도 델리미터로 감싸고 "데이터일 뿐" 지시 적용.
3. 배치 정규화(7.3절 `assert_sanity`)에 **문자열 필드 위생 검사** 추가: 제어문자 제거, 길이 상한, 지시문 패턴 로그 플래그.
4. `02-ai-strategy.md` 1.5절에 *"이 절의 방어는 온보딩 추출 호출에 한정된다. LLM을 사용하는 모든 호출은 개별적으로 이 표를 충족해야 한다"*를 명시.
- **담당 부서**: ai-optimization-engineer (주), backend-engineer (배치 위생 검사·계약 수정)

#### S-H6. 공공데이터 `serviceKey`가 예외 메시지 경유로 `raw_ingest_log.error_message`에 평문 적재

- **심각도**: High
- **위치**: `01-backend-design.md` 7.3절 `log.finish("failed", str(e))` (L816~818) x 5.2절 `raw_ingest_log.error_message TEXT` (L469) x 12.5절 *"실제로는 serviceKey 쿼리 파라미터일 가능성이 높으나"* (L1329) x 10.4절 *"URL 쿼리스트링 로깅 금지"* (L1189)

**문서가 스스로 세 조각의 모순을 드러낸다.**

- 10.4절은 공공데이터 API 키에 대해 **"URL 쿼리스트링 로깅 금지"**를 규칙으로 선언했다. (인지 자체는 우수)
- 12.5절은 **"실제로는 serviceKey 쿼리 파라미터일 가능성이 높다"**고 스스로 적었다. (공공데이터포털 관례상 정확한 예측)
- 7.3절 구현 의사코드는 예외 발생 시 **`log.finish("failed", str(e))`** 로 **예외 문자열을 통째로** `raw_ingest_log.error_message`에 저장한다.

`requests` / `httpx` / `aiohttp` 계열의 HTTP 예외 문자열에는 **요청 URL이 그대로 포함되는 것이 일반적**이다(ConnectionError, HTTPStatusError, Timeout 등). 즉 배치가 한 번만 실패해도:

```
raw_ingest_log.error_message = "...GET https://apis.data.go.kr/...?serviceKey=<실제 키 평문>&numOfRows=100..."
```

**사고 시나리오**: 침해 불필요. 정상 운영 중 공공 API가 타임아웃 한 번만 나면 **운영 DB 테이블에 API 키가 평문으로 영구 저장**된다. 이후 이 키는 (a) DB 백업, (b) 운영자 조회, (c) 장애 분석용 로그 수출, (d) 향후 관리자 화면 등으로 계속 확산된다. **키 유출은 되돌릴 수 없고 로테이션이 유일한 대응**이므로, 설계 단계에서 막지 못하면 실제로 못 막는 항목이다.

**추가 확산 경로 2건**
- 7.3절 `archive_raw(job.name, raw_pages)` — 원문 보관(P2 원칙) 시 요청 URL을 함께 저장하면 동일 문제.
- 7.3절 `alert("ingest_failed", job)` — 알림 채널(Slack/메일) 전송 시 동일.

**완화책**
1. `infra/http_client.py`에 **URL 새니타이저를 강제**한다: 예외를 잡아 serviceKey / apiKey / api_key / authKey / access_token / Authorization 파라미터를 `***`로 치환한 뒤 재raise. **모든 외부 호출이 이 클라이언트를 경유하도록 7.3절에 규정.**
2. `log.finish()` 내부에서 저장 직전 동일 마스킹을 **한 번 더** 적용(이중 방어 — 새 코드 경로가 생겨도 새지 않도록).
3. `archive_raw`는 **응답 본문만** 저장하고 요청 URL은 키 제거 후 저장.
4. 가능하면 **키를 쿼리스트링이 아닌 헤더로** 보낸다(포털이 지원하는 경우). Q-D9 확인 시 이 항목도 함께 확인 대상에 넣는다.
5. 10.4절의 규칙을 **선언이 아니라 강제 지점(코드 위치)과 함께** 기술한다.
- **담당 부서**: backend-engineer

#### S-H7. Tier C 혼잡도 / 로드밸런싱 카운터가 무인증 트래픽 기반 — 추천 결과의 외부 조작 가능

- **심각도**: High
- **위치**: `01-backend-design.md` 7.5절 Tier C 산출식(L869~871) / 8.2~8.3절 `record_guidance`(L942~992) x 6.1절 C2 `GET /places/{place_id}` **인증: 공개**(L543)

**어느 문서도 다루지 않은 신규 지적이다.**

Tier C(D1 확보 불가 시)의 혼잡도는 **서비스 자체 트래픽**으로 산출된다:
```
demand_signal(place) = 0.5 x norm(최근 3h 상세조회 수)
                     + 0.3 x norm(최근 3h 경로안내 발급 수)
                     + 0.2 x norm(최근 7d 저장 수)
```
로드밸런싱(8.2절)도 동일 신호를 쓴다:
```
weighted_count = 1.0 x 안내발급수 + 2.0 x 저장수 + 0.3 x 상세조회수
```

문제는 **이 카운터를 증가시키는 행위 중 상당수가 인증을 요구하지 않는다**는 점이다. `GET /places/{place_id}`(C2)는 **공개**, `POST /routes/compare`(D1)는 **선택**이다. rate limit도 IP 기준 60req/min(compare 10req/min)뿐이다.

**조작 시나리오 (방어 검증에 필요한 최소 기술)**
- **A. 혼잡도 부풀리기**: 특정 관광지의 상세조회를 반복 호출 → `demand_signal` 상승 → 전광판에서 혼잡(적색)으로 표시 → 해당 지역 상권에 실질적 불이익. 관광지 간 경쟁 관계에서 동기가 존재한다.
- **B. 로드밸런싱 조작**: 특정 코스의 `load_ratio`를 0.85 초과로 밀어올리면 8.3절 RED 상태가 되어 **그 코스가 추천에서 제외**된다. 반대로 경쟁 코스 카운터를 올려 자기 코스로 트래픽을 유도할 수도 있다.
- **C. 자기증폭 루프**: Tier C에서 `demand_signal`이 혼잡도를 만들고 그 혼잡도가 다시 로드밸런싱 판단에 쓰이므로 조작 효과가 두 시스템에 동시 전파된다.

**서비스적 함의**: 조작 가능한 것은 부가 기능이 아니라 **M2(전광판)·M6(로드밸런싱) = 공모전 "사회적 가치" 축의 핵심 증거**다. 심사위원이 "이 지표는 어떻게 신뢰하나"를 물을 가능성이 높은 지점이기도 하다.

**완화책**
1. **주체 단위 중복 제거**: 카운터 증가를 hash(guest_id 또는 user_id) 기준으로 dedupe — 동일 주체·동일 place는 **시간당 1회만** 계상. Redis `SETNX dedupe:{place}:{subject}:{hour}` 한 줄로 구현 가능.
2. **가중치 재조정**: viewed(0.3)는 가장 조작이 쉬우므로 Tier C에서 가중치를 낮추거나 dedupe 후에만 계상. saved(2.0)는 **이미 인증 필수 엔드포인트(E2)** 라 신뢰도가 높다 — **이 부분은 좋은 설계다.**
3. **이상 탐지**: `lb:cnt:*` 시간버킷 급증률이 임계치를 넘으면 알람 + 해당 버킷을 Tier C 산출에서 제외.
4. **Tier C 화면 표기 유지**: "서비스 내 관측 기반 추정치"는 이미 설계에 있다(P3 원칙). 심사 대응용으로 조작 방지 장치도 함께 설명할 수 있게 문서화.
5. 8.2절에 **"이 지표는 조작 가능한 신호이며 dedupe·이상탐지가 전제된다"**를 명시.
- **담당 부서**: backend-engineer (주), ai-optimization-engineer (Tier C 계수 재검토)

(기술적 결함이 아닌 **문서 정확성** 지적) | ai-opt |
| **S-L8** | `users.is_guest` 컬럼과 "게스트 DB 미기록" 정책 불일치 | 5.2절 `is_guest BOOLEAN` 및 CHECK 제약(L196·200) x 10.1절 *"Redis에 24h 보관 (DB 미기록)"*(L1153) | 게스트가 `users` 행을 갖는 경로가 존재하는지 불명확하다. 존재한다면 익명 사용자에 대한 **영구 레코드**가 생기는 것이라 10.1절의 "게스트는 이메일조차 수집하지 않는다"는 최소수집 논거가 약해진다. **완화**: 둘 중 하나로 확정 — (a) 게스트는 DB 행을 만들지 않는다(권장, `is_guest` 컬럼 삭제), 또는 (b) 만든다면 생성 조건·파기 시점을 명시 | backend |

## 3. 인증/인가 설계 검증 결과 (PRD 3번 항목 상세 답변)

### 3.1 `/me/*` IDOR — backend 자진신고에 대한 검증: **설계가 자진신고보다 양호하다**

backend는 13절에서 *"`/me/*`에서 path/body의 user_id를 신뢰하면 IDOR가 발생한다"*고 자진 신고했다. 실제 설계를 검증한 결과:

- 엔드포인트 목록(6.1절)의 `/me/*` 3종은 `/api/v1/me/routes`, `/api/v1/me/routes/{route_id}` — **`user_id` path parameter가 애초에 존재하지 않는다.**
- 10.3절 인가 규칙이 *"path의 user_id를 신뢰하지 않고 토큰의 sub만 사용"*을 명시.
- `saved_routes`의 PK가 `(user_id, route_id)` 복합키이므로 token.sub를 WHERE 절에 포함하면 타인 행에 도달할 수 없다.

**판정: 설계 수준에서 IDOR 표면이 구조적으로 차단되어 있다. 추가 완화 불필요.** 다만 S-L6(리뷰 수정·삭제 엔드포인트 미정의)이 같은 규칙의 사각지대이므로 `/me/` 네임스페이스로 편입할 것을 권고한다.

### 3.2 게스트 승격 프로필 탈취 — **완화책 불충분. S-H4 참조**

backend 자진신고 *"다른 guest_id의 프로필을 가로챌 수 없는지 확인 필요"*는 정확한 문제 제기였으나, **현재 문서에 완화책이 하나도 기술되어 있지 않다.** 오히려 `X-Guest-Id` 헤더(6.0절)와 HttpOnly 쿠키(10.2절)의 모순이 취약 구현을 유도하는 구조다. S-H4의 완화책 5개를 설계 문서에 반영해야 한다.

### 3.3 게스트 무인증 접근 범위 — **대체로 적절, 2건 조정 권고**

| 판정 | 내용 |
|---|---|
| 적절 | 게스트 제한이 **"저장·리뷰 작성"에만** 걸리고 조회·비교는 열려 있다(10.1절). 최소권한 원칙에 부합하며 "인증 없이 심사위원이 즉시 체험"이라는 PRD R5 목적도 충족한다. 게스트는 이메일조차 수집하지 않아 **개인정보 최소수집에 유리** |
| 적절 | 저장(E1~E4)이 인증 필수 → 로드밸런싱의 최고 가중치 신호(saved, 2.0)가 인증 트래픽 기반이라 조작 저항성이 있다 |
| 적절 | 배치 트리거 엔드포인트를 외부에 노출하지 않는다고 명시(10.3절) |
| 조정 | **A1(`/onboarding/analyze`)** — 무인증인데 외부 LLM 비용을 유발한다 → **S-M3** |
| 조정 | **C2(`/places/{place_id}`)** — 무인증인데 혼잡도·로드밸런싱 카운터를 증가시킨다 → **S-H7** |

**공통 원리**: "읽기 전용이니 공개해도 된다"가 성립하려면 **그 읽기가 부작용(side effect)을 만들지 않아야 한다.** A1은 비용을, C2는 상태(카운터)를 만든다. 무인증 엔드포인트의 부작용 유무를 기준으로 rate limit 등급을 재설계할 것을 권고한다.

## 4. Prompt Injection 방어 검증 결과 (PRD 2번 항목 상세 답변)

### 4.1 결론

**온보딩 추출 호출은 방어가 실질적으로 충분하다. 그러나 방어가 적용되지 않는 두 번째 LLM 호출이 존재한다(S-H5).**

### 4.2 우회 시도 결과 (방어 검증 목적, 익스플로잇 코드 미포함)

| # | 우회 시나리오 | 결과 | 근거 |
|---|---|---|---|
| 1 | 시스템 프롬프트 유출 시도 | **차단** | strict 모드 + additionalProperties false로 응답 형태가 스키마로 고정. 임의 텍스트 출력 채널이 없다 |
| 2 | 역할 변경 / 이전 지시 무시 | **차단** | 위와 동일. 모델이 지시를 따르려 해도 출력할 곳이 없다 |
| 3 | 스키마 밖 필드 생성 | **차단** | additionalProperties false + 서버 측 재검증(계층5) 이중 방어 |
| 4 | 태그 값 조작(스키마 내 합법 값 강제) | **부분 통과** | enum 내 값이므로 방어 우회가 아니라 **정상 동작**. 영향은 자기 계정 추천 품질에 한정. 단 `wheelchair_friendly` 등 **민감정보 필드가 허위로 세팅될 수 있음** → **S-M8** |

| 6 | **간접 인젝션(공공데이터 유래 문자열 → `build_verdict`)** | **통과 — 방어 없음** | 2차 LLM 호출에 1.5절 방어가 적용되지 않음 → **S-H5** |
| 7 | 토큰 폭주 / 비용 공격 | **부분 통과** | 300자 절단으로 요청당 비용은 제한되나 요청 **횟수** 제한이 없어 총액 방어 실패 → **S-M3** |
| 8 | 도구 호출·코드 실행·DB 조회 유도 | **차단** | 해당 LLM 호출에 도구·함수 권한 미부여(계층4). blast radius 최소화 설계가 정확하다 |

### 4.3 "LLM 출력이 그대로 DB 가중치가 되는 구조"에 대한 사실 확인

**PRD의 이 전제는 부분적으로만 참이다. 정확히는 다음과 같다.**

```
[사용자 자유텍스트]
      ↓ LLM (strict schema)
[tags — enum으로 값 집합이 고정된 구조체]     ← LLM이 결정하는 유일한 지점
      ↓ 서버 결정론 규칙 (02-ai-strategy 2.2절 가산표 + 정규화 공식)
[weight_vector]                                ← LLM이 만들지 않는다
      ↓
[스코어링 / 하드필터]
```

- **`weight_vector`는 LLM 출력이 아니다.** 2.2절의 가산 규칙표(회피우선이면 W_congestion에 0.10 가산 등)와 정규화 공식을 **서버 코드가** 적용해 산출한다. 따라서 LLM이 임의의 가중치 수치를 주입할 경로는 **없다.** 좋은 설계이며 정확히 평가되어야 한다.
- **서버 재검증의 실제 범위**: 1.5절 계층5는 *"JSON Schema로 재검증 후 DB 저장"* — 즉 **구조(shape)와 enum 소속만** 검증한다. 값 자체가 enum으로 닫혀 있으므로 이 수준으로 **충분하다.**
- **실제 공백은 다른 곳에 있다**: LLM 경로가 아니라 **클라이언트가 `weight_vector`를 직접 주입하는 경로**(6.2절 D1의 "또는 인라인 weight_vector")에 검증 규정이 없다 → **S-M1**. 즉 위협 모델이 "LLM이 나쁜 벡터를 만든다"가 아니라 **"클라이언트가 나쁜 벡터를 보낸다"**로 이동한다.

### 4.4 AI팀의 자체 위험 평가에 대한 검증

AI팀은 1.5절 말미에 *"인젝션의 최악 시나리오는 이상한 취향 태그가 하나 잘못 뽑히는 것 수준"*이라고 평가했다.

**보안팀 판정: 온보딩 호출에 한정하면 이 평가는 타당하다.** 단 두 가지 단서를 붙인다.
1. `accessibility`는 **하드 필터**(3.1절)이므로 태그 하나가 후보 집합 전체를 비운다. 다행히 후보가 비면 필터를 완화하는 폴백이 이미 있어 서비스 중단으로 이어지지 않는다(양호한 설계).
2. 잘못 뽑힌 태그가 `wheelchair_friendly`라면 그것은 "이상한 취향"이 아니라 **허위 민감정보의 생성·저장**이다. 프라이버시 영향은 추천 품질 영향보다 크다 → S-M8.

또한 AI팀이 남긴 *"향후 LLM에 도구 호출 권한을 부여하는 기능이 추가된다면 이 절을 반드시 재검토해야 한다"*는 단서는 정확하다. 보안팀은 여기에 **"LLM 호출을 새로 추가하는 경우"도 재검토 트리거에 포함**할 것을 추가 요구한다 — `build_verdict`가 바로 그 사례이며, 트리거가 없어 방어 없이 추가되었다(S-H5).

### 5.3 지도 SDK 키 — **도메인 제한 대책이 문서에 존재한다. 다만 보완 필요**

PRD가 물은 항목("클라이언트 노출이 불가피한데 대책이 있는가")에 대해:

> 10.4절: *"지도 SDK 키 | 클라이언트 노출 불가피 → **도메인 허용목록(referrer restriction) 필수** | 서버 키와 클라이언트 키를 혼용 금지"*

**판정: 필수 대책(도메인 제한 + 서버/클라이언트 키 분리)이 명시되어 있다. 요구사항 충족.**

**보안팀 추가 권고 3건**
1. **referrer 제한은 약한 통제임을 인지할 것.** Referer 헤더는 클라이언트가 위조 가능하므로 브라우저 외 환경(스크립트 직접 호출)에서는 우회된다. 따라서 **단독 통제로 신뢰하지 말고** 쿼터 알람·일일 사용량 모니터링을 함께 둔다. 실질 방어는 "유출을 막는 것"이 아니라 **"남용을 조기에 탐지하고 키를 교체하는 것"**이다.
2. **키 분리 원칙을 구체화.** 지도 표시용 JS 키와 경로탐색(길찾기) API 키(7.6절 snapped 대안이 의존)를 **별도 키로 발급**한다. 지도 키가 유출되어도 경로탐색 쿼터가 소진되지 않아야 한다.
3. **클라이언트 번들 노출 경계 명문화**(S-L5). Next.js에서는 NEXT_PUBLIC_ 접두사가 있는 값만 번들에 포함되므로 *"지도 SDK 키 외에는 NEXT_PUBLIC_ 접두사를 사용하지 않는다"*를 규칙으로 고정한다. LLM 키의 프론트 유입을 막는 실질 장치다.

### 5.4 결함: **선언과 강제 지점의 괴리** → S-H6

10.4절이 *"URL 쿼리스트링 로깅 금지"*를 선언했으나, 7.3절의 실제 구현 의사코드가 이를 위반한다. **규칙이 문서 한쪽에만 있고 구현 스케치에 반영되지 않은 전형적 사례**다. 보안 규칙은 "어디서 어떻게 강제되는가"까지 함께 적어야 구현자가 놓치지 않는다.

### 6.2 제3자·민감정보 유입에 대한 처리 방침 (PRD 명시 질의 답변)

> **PRD 질의**: *"자연어 온보딩 자유 서술에 딸려 들어오는 제3자 정보·민감정보(건강, 장애, 종교)를 어떻게 처리해야 하는가?"*

**보안팀 답변 — 4단계 방침을 설계 문서에 명문화할 것을 권고한다.**

1. **유입을 막으려 하지 말고, 유입을 전제하고 즉시 버려라.**
   "적지 마세요"라는 안내 문구는 자유 서술을 유도하는 UX와 근본적으로 충돌한다. 실효성 있는 통제는 **입력 차단이 아니라 저장 차단**이다. → **raw_input 미저장(S-H1)이 이 문제의 단일 최대 해법**이다. 원문을 버리면 "6세", "휠체어 타는 어머니", "성지순례" 같은 서술은 서버 어디에도 남지 않고, 남는 것은 `child_present: true` 같은 **의미가 통제된 boolean뿐**이다.

2. **구조화 태그로 좁히는 과정 자체를 프라이버시 통제로 인정하되, 그 통제가 실제로 좁히는지 검증하라.**
   AI팀의 enum + additionalProperties false 설계는 **의도치 않게 강력한 프라이버시 통제**로 기능한다 — "6세"라는 나이는 `child_present: true`로 축소되어 저장되고, 종교·질병명은 **스키마에 대응 필드가 없어 애초에 태그화되지 않는다**(`unmatched_note`로만 남으므로 S-M2 처리가 중요해진다). 이는 우수한 설계이며 문서에 **"태그 스키마는 프라이버시 축소 장치이기도 하다"**로 명시할 가치가 있다.
   **단 하나의 예외가 accessibility다** — 여기만은 건강·장애 정보가 **구조화 필드로 상시 저장**된다(P8). 유일한 예외이므로 별도 취급이 필요하다(S-M8).

3. **민감정보는 "추출"하지 말고 "사용자가 선택"하게 하라.**
   `wheelchair_friendly`를 LLM이 문장에서 추론해 저장하면 그것은 **동의 없이 수집한 민감정보**다. 반면 사용자가 온보딩 칩에서 "무장애 코스"를 **직접 클릭**하면 그것은 **정보주체의 명시적 제공**이다. 법적 성격이 전혀 다르다.
   설계에는 이미 A1(미리보기, 저장 없음) → A2(확정 저장)의 **human-in-the-loop 분리**가 존재한다. 여기에 *"accessibility 필드는 A1의 LLM 추출값을 자동 확정하지 않고, A2에서 사용자가 칩으로 확인·선택한 값만 저장한다"* 한 줄을 추가하면 문제가 해소된다. **구조 변경 없이 규정 추가만으로 가능하다.**

4. **제3자(아동·부모) 정보는 "관계 유형"까지만 남기고 "식별 가능성"을 남기지 마라.**
   현재 설계는 이미 이 원칙에 부합한다 — `companion: ["가족","아이동반"]`, `child_present: true`는 **동행 유형**이지 특정 아동을 식별하지 않는다. 나이·이름·성별을 저장하는 필드가 없다는 점은 **옳은 결정**이며, 향후 "아이 나이대별 추천" 같은 기능 요청이 와도 **연령 구간(예: 미취학/초등)까지만** 허용하고 정확한 나이를 저장하지 않는 선을 지켜야 한다. 이 원칙을 설계 문서에 못박아 둘 것을 권고한다.

| 조회 C1/D1 | **정밀 좌표(opt-in)** | **개인위치정보** (식별자 결합 시) | 위치정보법상 별도 동의 필요 (법률팀 L-1) |
| 리뷰·저장 E2/E4 | 리뷰 본문, 메모, 저장 이력 | 개인정보 | 미명시 |

### 7.2 저장

| 저장소 | 항목 | 기간 | 상태 |
|---|---|---|---|
| PostgreSQL `users` | 이메일, 비밀번호 해시, 표시명, status | **무기한** | 파기 절차 미명시 (S-M9) |
| PostgreSQL `user_profiles` | **raw_input 원문**, 태그, 가중치, region_code | **무기한** | 보관기간·파기 정책 부재 (S-H1) |
| PostgreSQL `reviews` / `saved_routes` | 리뷰 본문, 메모 | **무기한** | 탈퇴 시 처리 미명시 |
| Redis `session:guest:*` | 게스트 온보딩 프로필 | **24h** | 적절 |
| Redis `refresh:*` | 토큰 식별자 | **14d** | 적절 |
| Redis `ratelimit:*` | IP | 60s | 적절 |
| **Nginx access log** | **정밀 좌표 + guest_id** | **미명시** | 설계는 "비저장"이라 하나 실제로는 잔류 (S-H2) |
| PostgreSQL `raw_ingest_log` | (개인정보 아님) 단 **API 키 평문 유입** | 무기한 | S-H6 |
| 앱 access log | IP, UA, guest_id | **미명시** | 보관기간 규정 필요 (S-M9) |

### 7.3 전송 (제3자 제공 / 국외이전)

| 수신자 | 전송 항목 | 성격 | 상태 |
|---|---|---|---|
| **LLM API 사업자 (해외)** | 온보딩 자유 서술 **원문 전체**(300자 이내) | **국외이전** | **PII 스크러빙 없이 원문 그대로 전송**(S-M4). 벤더 ZDR·학습 미사용 옵션 확인 필요. 법률팀 L-5 |
| 지도 SDK (Kakao 등, 국내) | 지도 타일 요청 시 브라우저에서 SDK 서버로 직접 통신. **Referer 헤더에 좌표 쿼리스트링이 실릴 수 있음** | 개인위치정보 간접 유출 가능 | S-H2 완화 시 함께 해소 |
| 공공데이터 API | **개인정보 전송 없음** (배치가 단방향 수집만) | — | 양호 |
| **미동의 대체 경로** | 칩 전용 입력은 **LLM 미호출** | — | **국외이전 없이 서비스가 온전히 동작하는 경로가 이미 설계에 존재**(AI 1.2절). 동의 거부 사용자 대응에 활용 가능 |

### 7.4 파기

| 계기 | 현재 설계 | 필요 조치 |
|---|---|---|
| 게스트 세션 만료 | Redis TTL 24h 자동 파기 | 적절 |
| 회원 탈퇴 | soft delete(status)와 hard delete(ON DELETE CASCADE)가 **혼재** | 어느 쪽인지 확정 필요. `user_profiles`는 **지체 없이 hard delete** 권고 (S-M9) |
| raw_input 보관기간 만료 | **파기 로직 없음** | 미저장 전환, 또는 30일 TTL 컬럼 + 일 1회 파기 배치 신설 (S-H1) |
| 접근 로그 | **보관기간 규정 없음** | 3개월 이내 자동 파기 (S-M9) |
| 리뷰 (탈퇴 후) | 미명시 | 파기 vs 작성자 익명화 후 유지 — **정책 결정 필요** |

### 7.5 법률팀에 요청하는 추가 판정 3건

## 8. 잘 설계된 부분 (유지 권고 — 재작업 시 훼손 금지)

균형 잡힌 판정을 위해 명시한다. 아래는 **설계 단계에서 보기 드물게 잘 잡힌 항목**이며, High 이슈를 수정하는 과정에서 훼손되지 않아야 한다.

1. **N1(EXIF·사진 인증) 컬럼을 의도적으로 만들지 않음** (11.3절) — *"스키마에 자리를 만들어 두면 다음 단계에서 자동으로 구현 대상이 된다"*는 판단은 privacy-by-design의 정확한 실천이다. **이번 검토에서 가장 우수한 설계 결정.**
2. **토큰 저장 전략** — access는 메모리(localStorage 금지 명시), refresh는 HttpOnly·Secure 쿠키 + rotation + **재사용 탐지 시 전체 세션 무효화**. 설계 단계에서 여기까지 규정한 경우는 드물다.
3. **`/me/*`에 user_id path parameter를 두지 않은 구조** — IDOR을 규칙이 아니라 **URL 구조로** 차단했다.
4. **weight_vector를 LLM이 아닌 서버 결정론 규칙이 생성** — LLM 출력의 blast radius를 태그 선택으로 한정.
5. **LLM 호출에 도구·함수 권한 미부여** (AI 1.5절 계층4) — 인젝션 최악 시나리오를 구조적으로 제한.
6. **A1/A2 분리(미리보기 → 확정 저장)** — human-in-the-loop 지점이 이미 존재해 S-M8 완화가 규정 추가만으로 가능하다.
7. **칩 전용 입력이 LLM을 우회**(AI 1.2절) — 성능 최적화로 설계되었으나 결과적으로 **국외이전 미동의 사용자를 위한 완전한 대체 경로**를 제공한다. 법률 리스크 완화 자산으로 활용할 것.
8. **시크릿 관리 규칙 사전 정의**(10.4절) — gitleaks pre-commit, 부팅 fail-fast, 지도 SDK 도메인 제한까지 설계 단계에서 규정.
9. **P1 원칙(읽기 경로에서 외부 API 미호출)** — 가용성 목적으로 설계되었으나 **SSRF 표면을 구조적으로 제거**하는 부수 효과가 있다.
10. **게스트가 이메일조차 수집하지 않는 구조 + Redis 24h TTL** — 개인정보 최소수집의 모범 사례.
11. **backend·AI 양팀의 "확인 필요" 정직 표기** — 26건/7건을 추측으로 채우지 않고 집계한 태도가 이번 보안 검토를 가능하게 했다. 문서가 스스로 모순을 드러낸 덕분에 S-H6·S-H3 같은 항목을 찾을 수 있었다.

## 12.1 이번 라운드 판정

# **Critical 0건 / High 1건 / Medium 2건 / Low 2건**

### 3차 게이트(보안 측) 판정: **통과 (조건부 승인 유지)**

- **Critical 0건** → CLAUDE.md 3차 게이트 통과 조건 충족. **M8~M10 재도입이 게이트를 되돌리지 않는다.**
- 신규 High 1건(**S-H8, EXIF 미제거**)은 1라운드 High들과 동일 성격 — "설계에서 안 잡으면 구현에서 못 잡는 것"이다. 구현 착수 전 설계 문서 반영을 조건으로 한다. 미반영 상태로 코드가 작성되면 그 시점에 **Critical로 격상**한다.
- 대표 최종 결재를 막지 않는다. 누적 조건은 **"설계 묶음 승인 + High 8건(1라운드 7 + 이번 1) 구현 착수 전 반영"**이다.

### 총평 — M8 설계는 R10 제약을 정직하게 흡수했다

backend의 M8 설계는 **위조를 막을 수 있다고 과신하지 않는다**(§15.1.6이 브라우저 Geolocation 스푸핑·사진 재사용을 명시적으로 인정). 원좌표 미저장(distance_m만 저장), 쿠폰 미결합(grep 실측, §15.6), review_trust/스코어링 격리(J6 재발 방지, §15.0), 좌표 body 전송(§3.1 S-H2 교훈 반영)은 모두 **1라운드 지적을 학습한 흔적**이다. **결함은 단 하나의 축 — 사진 파일에 남는 EXIF — 에 집중된다.**

## 12.2 항목별 검토 결과 (backend 재검토 요청 A~F 대조)

### A. M8 사진 업로드 공격 표면

| 점검 | 결과 | 근거 |
|---|---|---|
| 파일 **용량** 제한 | **설계됨** | §15.1.4 `object_store.put(..., max_bytes=8*1024*1024)` — 8MB 캡이 의사코드에 존재. 값(8MB)은 가정값(Q-M7, 확인 필요)이나 제한 자체는 설계됨 |
| 파일 **타입** 제한 | **미흡 (강제 없음)** | H1 주석에 image/jpeg·png만 있고 **의사코드에 매직바이트 검증·재인코딩이 없다.** Content-Type은 클라이언트가 위조 가능 → **S-M11** |
| **EXIF 제거** 파이프라인 | **결함 (선택적 처리)** | §15.1.4 주석 `# EXIF 미파싱. 필요 시 저장 전 EXIF strip` — **"필요 시"는 강제가 아니다.** "신뢰하지 않음"과 "저장 전 제거"는 다르다 → **S-H8** |
| 스토리지 **접근 권한** | **미명시** | `photo_ref='s3://.../visit/{uuid}.jpg'`. UUID 경로라 순회는 비현실적이나 **버킷 ACL(공개/비공개)·서명 URL 여부 미규정** → **S-M12** |
| rate limit / dedupe | **적절 (형식적 아님)** | §15.1.5 `SETNX visit:done` 24h 잠금 + `INCR visit:try` 일 5회 + HMAC user_hash. **H1이 인증 필수**라 주체 단위 억제가 실효적. 무인증 남용 표면 없음 |

**판정**: 용량·rate limit·dedupe·주체 격리는 양호. **타입 검증(S-M11)·EXIF 제거(S-H8)·버킷 ACL(S-M12) 3건이 신규 지적.**

### B. M8 GPS 좌표 처리

- **서버 검증 방식**: 클라이언트(브라우저 Geolocation)가 body로 보낸 좌표를 서버가 haversine으로 거리 계산 후 임계값(150m 가정) 비교. **좌표를 쿼리스트링이 아닌 body로 받는다**(§3.1 L1 승계) → S-H2 로그 잔류 문제를 이미 회피. **양호.**
- **스푸핑 인정 여부**: §15.1.6이 *"서버 수신 좌표도 결국 클라이언트 신고값이며 진위를 보장하지 않는다"*고 **정직하게 인정**한다. **과신 서술 없음.** 이 문제는 웹 환경에서 완전히 막을 수 없으며(네이티브 App Attest 부재), 설계가 이를 숨기지 않고 "보조 신호 + 비금전 배지"로 영향을 한정한 것은 R10 제약의 올바른 흡수다. **추가 지적 없음.**
- **좌표 저장 범위**: `visit_verifications`에 **원좌표 컬럼을 만들지 않고 distance_m(정수)만 저장**(§15.1.2). 3자리 반올림 권장(§3.1 L2). **최소수집 원칙(R4)과 정확히 일치. 우수.** 단, 이 좌표 최소화의 성과가 **사진 EXIF로 되살아나는 것이 S-H8의 핵심**이다.

### C. M9 오디오 URL 재배포 / hotlinking

- **인지됨**. §15.2.2가 *"오디오 바이트를 서버가 프록시하지 않는다 — 메타데이터 + 원천 스트리밍 URL만 전달, 재생은 클라이언트가 원천 URL로 직접"*으로 설계해 **우리 서버 대역폭·재배포 프록시 리스크를 회피**한다. 동시에 *"원천 URL의 재배포 허용 여부는 확인 필요(Q-D13)"*로 **원본 저작권자 관점의 hotlinking/재배포 허용 문제를 명시적으로 플래그**했다.
- **보안 판정**: 프록시 미채택은 SSRF·대역폭 관점에서 오히려 안전한 선택. **재배포 허용 여부는 보안이 아니라 라이선스/이용약관 이슈**로, Q-D13이 이미 legal 대상으로 지정. **보안 신규 지적 없음** — 다만 M9 응답의 `title` 등 외부데이터 유래 문자열이 화면에 렌더되므로 S-M7(출력 인코딩) 원칙을 M9에도 적용해야 함 → **S-L10**.

### D. M10 Tmap API 키 관리

- **서버 프록시 구조 — 양호.** M10 실연동(안 a)은 **backend 엔드포인트 `J1 POST /api/v1/routes/directions`**로 구현된다(§15.3.1). 즉 **Tmap Route API 키는 서버가 보관·사용하며 클라이언트 번들에 노출되지 않는다.** 지도 *표시* SDK(Kakao, 클라이언트 노출 불가피 → 1라운드 5.3절 referrer 제한 대상)와 **키가 분리**된다. 딥링크 폴백(안 b)은 키가 필요 없다.
- §15.7 핸드오프가 *"Tmap 키는 §10.4 시크릿 하드코딩 금지·ENV 규칙 적용 대상"*으로 명시. **요구사항 충족.** 키/쿼터/과금은 Q-M5(P0, 확인 필요)로 집계됨.
- **보안 신규 지적 없음.** 단, J1은 외부(Tmap) 호출이므로 1라운드 **S-H6(예외 메시지 URL 새니타이저)의 적용 범위에 J1도 포함**되어야 한다(Tmap 키가 예외 URL로 로그에 새지 않도록). 이는 S-H6의 확장 적용이지 신규 항목이 아니다.

### E. 08 정본 침범 / 클라이언트 인증 상태 위조 (보안 관점)

- **위조된 인증 배지를 클라이언트가 스스로 부여할 수 있는가? → 아니오. 구조적으로 차단됨.**
  - H1 응답의 `status`("verified"/"rejected")는 **서버가 haversine 거리로 산출**한다(§15.1.4). 클라이언트는 좌표·사진만 제출하며 **"status"·"badge.granted"를 body로 주입하는 경로가 없다.** 위조 가능한 것은 *좌표값*(= 위치 스푸핑, §15.1.6이 인정한 한계)이지 *판정 결과*가 아니다.
  - `visit_verifications`는 `reviews`·`review_trust`·스코어링과 **조인되지 않는 독립 테이블**이며 compare 34필드에 어떤 값도 주입하지 않는다(§15.0). **J6(인증→신뢰도) 회귀 없음** — QA 최우선 재검수 항목과 일치.
- **판정**: 08 정본 불가침. 클라이언트 발(發) 배지 위조 표면 없음. **양호 (신규 지적 없음).**

## 12.3 신규 취약점 (M8~M10)

### S-H8. 방문 인증 사진의 **EXIF 미제거** — 최소수집으로 버린 정밀 위치·기기정보가 사진에 되살아남

- **심각도**: High (구현 시 Critical)
- **위치**: `01-backend-design.md` §15.1.4 `object_store.put(photo, prefix="visit/", max_bytes=8MB)  # EXIF 미파싱. 필요 시 저장 전 EXIF strip` (L2092~2093) × §15.1.2 스키마 주석 *"원좌표·EXIF 컬럼을 만들지 않는다"*(L2016~2018) × V3/V4(L2008~2009)

**설계가 스스로 만든 모순이다.**

§15.1.2와 V4는 *"식별자와 결합된 정밀 좌표는 개인위치정보이므로 원좌표를 저장하지 않고 distance_m만 남긴다"*고 명시하며, 이것을 M8 프라이버시 설계의 핵심 성과로 내세운다(§15.1.2 하단 주석). **그런데 같은 함수가 사진 원본을 오브젝트 스토리지에 7일간 그대로 저장한다.** 스마트폰 카메라 원본 JPEG은 통상 EXIF에 **GPS 좌표(위·경도, 미터급 정밀도)·촬영시각·기기 제조사/모델**을 임베드한다.

- "EXIF를 **신뢰하지 않는다**"(V3, 파싱하지 않음)와 "EXIF를 **제거한다**"는 전혀 다르다. 파싱하지 않아도 **파일 안에는 그대로 남는다.**
- 결과: `visit_verifications`는 distance_m만 갖지만, 그 행의 `photo_ref`가 가리키는 **사진 파일에는 user_id와 결합된 정밀 GPS + 기기 지문이 7일간 상주**한다. 테이블에서 애써 뺀 개인위치정보가 스토리지로 자리만 옮겨 되살아난다. **정밀도는 distance_m(반경 판정)보다 오히려 높다.**
- "필요 시 저장 전 EXIF strip"의 **"필요 시"는 강제가 아니다.** 구현자가 이 주석을 읽으면 "지금은 안 해도 됨"으로 해석해 건너뛴다. 전형적인 "설계에서 안 잡으면 못 잡는" 항목.

**사고 시나리오**: 침해 불필요. 정상 운영만으로 오브젝트 스토리지 버킷(+ 그 백업)에 사용자별 정밀 위치·기기정보가 담긴 사진이 축적된다. S-M12(버킷 ACL 미명시)와 결합하면 유출 표면이 커진다.

**완화책 (설계 문서에 지금 반영)**
1. **저장 전 EXIF strip을 "필요 시"가 아니라 무조건 강제한다.** §15.1.4를 *"모든 업로드 사진은 저장 전 메타데이터 전체(EXIF/XMP/IPTC) 제거를 거친다"*로 못박고, 강제 지점(코드 위치)을 함께 적는다(1라운드 S-H6과 동일한 "선언+강제 지점" 원칙).
2. **재인코딩으로 일괄 해결.** 서버에서 사진을 이미지 라이브러리로 **디코드 후 재인코딩**(예: Pillow로 RGB 재저장)하면 EXIF/XMP가 자연히 소거되고 **S-M11(타입 위장·폴리글롯)까지 동시 차단**된다. 한 조치로 High+Medium 동시 해소 — 권장.
3. V4 문구에 *"원좌표뿐 아니라 사진에 임베드된 위치·기기 메타데이터도 저장하지 않는다"*를 추가해 최소수집 주장을 사진까지 확장한다.
- **담당 부서**: backend-engineer (업로드 파이프라인·EXIF strip 강제)

### S-M11. 사진 파일 타입 검증이 강제되지 않음 (Content-Type 신뢰)

- **심각도**: Medium
- **위치**: `01-backend-design.md` §15.1.3 H1 주석 *"image/jpeg|png"*(L2057) × §15.1.4 `object_store.put`(L2092) — 의사코드에 타입 검증 단계 부재
- H1 주석에 허용 타입이 있으나 **의사코드에는 매직바이트 검증·확장자 검증·재인코딩이 없다.** Content-Type 헤더는 클라이언트가 위조 가능하므로 SVG(스크립트 내장)·폴리글롯·비이미지 파일이 업로드·저장될 수 있다.
- **완화책**: (a) 매직바이트(파일 시그니처)로 실제 포맷 확인, image/jpeg·png 외 거부, (b) **저장 전 재인코딩**(S-H8 완화책 2와 동일 모듈 — EXIF strip과 함께 처리), (c) `Content-Disposition: attachment` + 별도 도메인 서빙으로 렌더 컨텍스트 격리, (d) 8MB 캡을 **스트리밍 단계에서** 적용해 대용량 버퍼링 메모리 소모 방지.
- **완화 난이도 낮음**: 사진이 API 응답으로 재서빙되지 않아(H1~H3 응답에 photo URL 없음) 저장형 XSS 실현 경로가 짧다 → 그래서 High가 아닌 Medium. 단 S-M12에서 버킷이 공개로 구성되면 실현 경로가 생긴다.
- **담당 부서**: backend-engineer

### S-M12. 사진 오브젝트 스토리지 **버킷 접근 권한·서빙 방식 미명시**

- **심각도**: Medium
- **위치**: `01-backend-design.md` §15.1.2 `photo_ref TEXT -- 's3://.../visit/{uuid}.jpg'`(L2031) × §15.1.4 `object_store.put`(L2092) — 버킷 ACL·서빙 경로 미규정
- 사진 원본을 오브젝트 스토리지에 두고 참조만 DB에 저장하나, **버킷이 public-read인지 private인지, 사진을 다시 서빙한다면 서명 URL을 쓰는지**가 어느 문서에도 없다. UUIDv4 경로라 URL 순회·추측은 비현실적이지만 **UUID는 접근 통제가 아니다** — 버킷이 공개로 구성되면 유출·오인덱싱(검색엔진 크롤) 위험, S-H8(EXIF)과 결합 시 정밀 위치·기기정보 유출.
- **완화책**: (a) 버킷을 **비공개(public access block)**로 강제 명시, (b) 사진 조회가 필요하면 **소유자 스코프 + 단기 서명 URL(예: 60초)**로만 발급하고 원본 URL을 API 응답에 직접 싣지 않음(현재 H1~H3 응답에 없음 — 유지), (c) 버킷 정책·수명주기(7일 TTL 파기)를 `visit_verifications.photo_expires_at` 파기 배치(`job_visit_photo_purge`)와 정합, (d) 버킷 로깅 자체가 URL에 개인정보를 남기지 않는지 확인.
- **담당 부서**: backend-engineer, 대표(인프라 결정)

### S-L9. 업로드 사진에 대한 콘텐츠(악성코드) 스캔 부재

- **심각도**: Low
- **위치**: §15.1.4 업로드 파이프라인 — AV/콘텐츠 스캔 언급 없음
- 사진이 **재서빙·실행되지 않고 7일 TTL로 파기**되어 blast radius가 작아 Low. 다만 저장소가 다른 시스템(백업·운영자 다운로드)으로 확산될 수 있으므로, 재인코딩(S-H8/S-M11)을 적용하면 대부분의 임베드 페이로드가 함께 무력화되어 별도 AV 없이도 실질 위험이 낮아진다. **완화**: 재인코딩을 1차 방어로 하고, 운영 규모 확대 시 오브젝트 스토리지 연동 AV 스캔 도입 검토.
- **담당 부서**: backend-engineer

### S-L10. M9 오디오 메타데이터(외부데이터 유래 문자열) 출력 인코딩 — S-M7 원칙의 M9 확장

- **심각도**: Low
- **위치**: `01-backend-design.md` §15.2.2 I1 응답 `title`, `03-design-spec.md` §13.2 오디오 행 렌더
- 오디오 가이드 `title`·`stream_url`은 **외부(오디 API) 유래 문자열**이며 M9 플레이어에 렌더된다. 1라운드 S-H5/S-M7과 동일 뿌리(외부/LLM 유래 문자열의 무검증 렌더). `stream_url`은 `href`/재생 소스로 쓰이므로 `javascript:` 스킴 필터링도 필요. **완화**: (a) S-M7의 *"외부데이터 유래 문자열은 텍스트 노드로만 렌더, dangerouslySetInnerHTML 금지"* 원칙을 M9에 명시 적용, (b) `stream_url`은 `https:` 스킴 화이트리스트 검증 후에만 재생 소스로 사용, (c) 제목 길이 상한.
- **담당 부서**: designer, backend-engineer

## 12.4 잘 설계된 부분 (M8~M10, 유지 권고 — 재작업 시 훼손 금지)

1. **§15.1.6 한계의 정직한 명시** — 브라우저 Geolocation 스푸핑·서버 수신 좌표의 신고값 성격·사진 재사용 불가증명을 **숨기지 않고 인정**하고 영향을 "보조 신호 + 비금전 배지"로 한정. R10 제약을 과신 없이 흡수한 모범.
2. **원좌표 미저장(distance_m만)** — 최소수집(R4)의 정확한 실천. (단 사진 EXIF로 되살아나는 것이 S-H8.)
3. **쿠폰 미결합 grep 실측(§15.6)** — R10 제약 2를 선언이 아니라 도구로 검증. M8 설계 본문 0건 확인.
4. **`visit_verifications` 독립 테이블 + review_trust/스코어링 격리(§15.0)** — J6(인증→신뢰도) 회귀를 구조로 차단. 클라이언트 발 배지 위조 표면 없음(status 서버 산출).
5. **좌표 body 전송(§3.1 L1 승계)** — 1라운드 S-H2(쿼리스트링 로그 잔류) 교훈을 M8에 선반영.
6. **M10 Tmap 키의 서버측 보관(J1 엔드포인트)** — 경로탐색 키를 클라이언트에 노출하지 않고 지도 표시 SDK 키와 분리.
7. **M9 오디오 바이트 프록시 미채택 + 재배포 허용 여부 플래그(Q-D13)** — SSRF·대역폭 표면 회피 + 저작권 이슈 정직 표기.

## 12.6 법률팀 전달 — M8~M10 개인정보/데이터 처리 이슈 (7절 증분)

> 1라운드 §7 흐름 요약에 M8~M10을 추가한다. backend §15.5가 이미 legal 대상으로 지정한 Q-L5·Q-L6·Q-L7·Q-D13과 정합한다.

| # | 질의 | 배경 | backend Q-ID |
|---|---|---|---|
| **SEC→L-D** | M8 방문 사진에 **EXIF GPS/기기정보가 잔류하면**(S-H8 미조치 시) 이는 "원좌표 비저장" 주장과 무관하게 **개인위치정보 수집·보관**에 해당하는가? EXIF 전면 제거를 조건으로 위치정보 수집 판정이 달라지는가 | S-H8. 사진 EXIF가 distance_m보다 정밀한 위치를 7일 보관 | Q-L5 연장 |
| **SEC→L-E** | M8 **방문 사진의 초상권·타인 얼굴 포함** 처리와 7일 TTL 보관의 개인정보 적정성 | S-M12·P25 | Q-L6 |
| **SEC→L-F** | 약한 현장 신호에 **"인증"이라는 표현**을 쓸 때 소비자 오인 소지(§15.1.3 notice가 완화하나 문구 확정 필요) | 배지 문구 | Q-L7 |
| **SEC→L-G** | M9 **원천 오디오 스트리밍 URL을 클라이언트에 재전달**하는 것이 원저작권자 이용약관상 재배포/임베드 허용 범위인가 | §15.2.2, hotlinking | Q-D13 |

**법률팀이 우선 볼 것**: **SEC→L-D(사진 EXIF의 위치정보 해당성)** 와 **SEC→L-E(사진 초상권)** — 둘 다 M8이 재도입한 "사진"이라는 신규 수집물에 직결되며, 1라운드 L-1(위치기반서비스사업자 신고 판정)의 사실관계를 M8이 바꾼다.

## 12.7 담당 부서별 조치 요약 (M8~M10 증분)

### backend-engineer (High 1 / Medium 2 / Low 1)

## 12.8 M8~M10 최종 판정

### **조건부 승인 — 3차 게이트(보안 측) 통과 (Critical 0건 유지)**

| 구분 | 내용 |
|---|---|
| **이번 라운드 판정** | Critical 0 / **High 1(S-H8)** / Medium 2(S-M11·S-M12) / Low 2(S-L9·S-L10) |
| **게이트 판정** | **통과.** M8~M10 재도입이 Critical을 만들지 않았다. 개인정보(위치+사진) 재도입에도 게이트 조건 충족 |
| **승인 성격** | **조건부(1라운드 승계).** 누적 High 8건을 구현 착수 전 설계 문서에 반영. 미반영 코드 착수 시 Critical 격상 |
| **재작업 요청** | **없음.** 발견 이슈는 전부 문서 보완으로 해소 가능(EXIF strip 강제·타입 검증·버킷 ACL 명문화). 부서 재작업 왕복 사유 아님 |
| **대표 최종 결재** | **막지 않는다.** M8의 R10 제약 흡수(과신 없음·쿠폰 미결합·J6 격리)는 양호. 단 사진 EXIF 1건은 "위치 최소수집 성과를 되살리지 않도록" 반드시 반영 조건 |

**한 줄 총평**: M8 설계는 1라운드 지적(S-H2 좌표·최소수집)을 학습해 좌표를 잘 다뤘으나, **같은 원칙을 사진 파일까지 확장하지 못했다** — 버린 정밀 위치가 EXIF로 되살아나는 단 하나의 축(S-H8)이 이번 라운드의 실질 결함이며, **저장 전 재인코딩 한 조치로 S-H8·S-M11·S-L9가 동시에 해소**된다.
