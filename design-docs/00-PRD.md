## 1. 문제 정의

### 1.1 사용자 문제 (초안에서 승계)
1. **오버투어리즘 쏠림** — 특정 유명 관광지 병목으로 대기·피로도 증가, 주민 갈등 유발.
2. **획일화된 추천** — 기존 여행 앱은 동행자 맥락(연인/혼여행/아이+반려동물/부모님)을 반영하지 못하고 단일 핫플 위주 추천.
3. **로컬 상권 소외** — 메인 관광지 인근 로컬 상점·공방·둘레길이 홍보 부족으로 외면.

### 1.2 이번 파이프라인이 푸는 문제 (메타 문제)
초안은 **기획 언어**로 쓰여 있고 **구현 언어**로 번역되어 있지 않다. 구체적으로:
- "AI 1:1 대조 경로"가 어떤 입력·연산·출력을 갖는지 정의되지 않음 (알고리즘 미정의).
- "자연어 온보딩 NLP"가 KoNLPy인지 LLM인지 이중 표기되어 기술 선택이 미결.
- 연동한다고 선언된 API 12종 이상이 **실제로 제공되는지, 어떤 필드·갱신주기·쿼터인지** 검증되지 않음.
- 8주 로드맵이 있으나 **공모전 제출 기준 MVP 경계**가 없어 전부 필수처럼 읽힘.
- Geo-location/EXIF 인증, 개인정보 수집 범위 등 **기술·법적 위험이 무비판적으로 확정 서술**됨.

→ 이번 단계의 문제는 "숨은길을 만드는 것"이 아니라 **"숨은길을 만들 수 있는 상태로 만드는 것"**이다.

## 2. 목표 및 성공 기준

### 2.1 목표
초안을 근거로, **backend / AI / design 3개 부서의 설계 산출물 묶음**을 산출하여 (a) 공모전 기획서 본안 작성과 (b) 후속 실제 구현이 모두 가능한 상태로 만든다.

## 3. 스코프 / 논스코프

### 3.1 MVP 판정 기준
공모전 웹·앱 구현 부문은 **"지정 관광데이터를 실제로 활용한 동작하는 결과물"**이 핵심이다. 따라서 MVP 판정 기준을 다음 3가지로 둔다.
1. 공공 관광데이터를 직접 소비하는가?
2. 지정과제(오버투어리즘 분산)의 인과를 심사위원에게 시연할 수 있는가?
3. 이 기능 없이 서비스 서사가 성립하는가? (성립하면 후순위)

### 3.2 MVP — 공모전 제출용

> **2026-07-23 대표 지시로 개정.** "대회 공식 개발 체크리스트를 먼저 따라" — R10에서 제기한 N1(사진 인증) 충돌뿐 아니라, `_공모전분석-대회요강.md` 5.2절 공식 체크리스트 전체를 스코프 결정의 상위 기준으로 삼는다. 체크리스트에 명시된 항목은 기존에 후순위(N)로 뺐더라도 MVP로 승격한다. 체크리스트에 없는 항목(쿠폰·PWA·BM 등)은 기존 판단을 유지한다.
>
> ### ⚠️ 정정 (2026-07-24) — 아래 표의 "요강 체크리스트 명시 항목" 근거는 틀렸다
> 대표가 **진짜 공식 공고문 PDF**(`_공모전_공고문-원본.md`, 한국관광공사 발행)를 제공했다. 대조 결과, `_공모전분석-대회요강.md`(제3자가 정리한 참고 분석 자료였음, 공식 공고문 아님)의 "개발 로드맵 체크리스트"는 **실제 공고문에 없는 내용**이었다. 진짜 공고문의 필수 요건은 단 하나뿐이다:
> > **"② 한국관광공사 OpenAPI 활용 필수 — 최종 완성 서비스 내 한국관광공사 OpenAPI를 필수로 활용하여야 합니다. ※ 그 외 외부 API 자유롭게 추가 활용 가능합니다."**
>
> "Kakao/NAVER Maps SDK 및 Tmap Route API 연동", "웹 Geo-location + 사진 인증 모듈", "오디오 가이드 API 연동", "두루누비"·"전국문화축제" 등은 **공고문 어디에도 명시된 필수 요건이 아니다.** 붙임의 "(예시) 서비스"도 공고문 12페이지가 "참고용 예시이며 개발 의무나 이익/불이익 없음"이라고 명시적으로 disclaim하고 있다.
>
> **아래 M8~M12의 "요강 체크리스트 명시 항목" 근거는 전부 무효다.** 기능 자체를 지금 되돌리지는 않는다(이미 설계가 진행됐고, 개별적으로는 여전히 가치 있는 기능일 수 있다) — 다만 **"필수라서"가 아니라 "선택적으로 좋다고 판단해서"로 근거가 바뀐다.** 특히 M8(사진 인증)은 R3가 지적한 보안·개인정보 비용이 여전히 유효한 채로, 더 이상 "안 하면 감점"이 아닌 순수 선택 사항이 됐다 — 대표가 계속 가져갈지 재검토할 여지가 있다.

| N8 | **실제 배포/인프라 구축** | 이번 파이프라인의 최종 결재 대상이 아님 (4절) |

### 3.4 이번 파이프라인이 하지 않는 것 (프로세스 논스코프)
- 실제 코드 구현 및 배포 — 설계·명세·시안까지만.
- 공공데이터 API 실제 호출 테스트 — **키 발급 여부 확인 필요** (5절 R1). 부서는 문서 기반으로 설계하고 미확인은 "확인 필요"로 표기.
- 공모전 제출 서류 본문 작성 — 후속 단계(content-marketer)에서 수행.

## 4. 최종 결재 대상 (CLAUDE.md 결재 규칙)

> **이 프로젝트의 "최종"은 배포가 아니라 "구현 설계 + 디자인 시안 산출물 묶음"이다.**

**근거**: 대표 지시가 "초안인 만큼 안의 기능 구현과 대략적인 디자인들을 구상해줘"이며, 배포 대상 인프라·도메인·API 키가 확보되지 않았고, 공모전 제출물 자체도 아직 본안이 아니다.

**최종 결재물 정의**:
```
projects/sumeungil/
  00-PRD.md              ← 본 문서
  01-backend-design.md   ← API/DB/데이터 파이프라인 설계
  02-ai-strategy.md      ← NLP 온보딩 + 경로 스코어링 + 로드밸런싱 전략
  03-design-spec.md      ← 화면 5종 와이어프레임 + 디자인 시스템
```
위 4개 파일 묶음이 완성되고 3차(QA/보안)·4차(법률) 게이트를 통과한 시점에 **대표에게 최종 결재를 요청**한다. 대표가 승인하면 이 묶음이 "1안 확정 설계"가 되고, 실제 구현 착수는 **별도 후속 프로젝트**로 분리한다.

**게이트 등급 사전 지정** (CLAUDE.md 검수 경량화 규칙):
- 3차 게이트 = **약식** (본 단계 산출물은 문서이며 코드 변경 없음). 단, 개인정보·위치정보·EXIF를 문서상 다루므로 **security-engineer가 "설계상 개인정보 수집 범위"만 좁게 검토**하도록 예외 지정.
- 4차 게이트 = **필수 수행**. 위치정보법·개인정보보호법·공공데이터 이용약관·지도 SDK 라이선스가 걸려 있음 (5절 R4/R6).

## 5. 초안의 빈틈 / 리스크

> 원칙: 초안이 단정한 것 중 **근거가 확인되지 않은 것**은 모두 "확인 필요"로 분리했다. 아래 항목을 사실로 간주하고 설계하지 말 것.

### R1. 공공데이터 API 실재성 — **부분 확인됨, 방법론까지 확인 (2026-07-23 갱신)**
초안 7절은 12종 이상 데이터셋을 "확정 데이터셋 연동 명세"라고 단정했고, 최초 PRD 작성 시점엔 검증 근거가 없었다.
- **확인됨 (2026-07-22, api.visitkorea.or.kr 개발자 포털 직접 확인)**: "한국관광공사_관광지 집중률 방문자 추이 예측 정보" (data.go.kr `15128555`) — **REST API로 실재한다.** 조회일 기준 향후 30일 관광지별 집중률 방문자 추이 예측치 제공. 개발계정 일 1,000회, 운영계정은 활용사례 등록 시 확대, 개발단계 자동승인, 무료.
- **방법론 확인됨 (2026-07-23, data.go.kr 상세설명 확인)**: 이 데이터는 **실측(센서/CCTV 계수)이 아니라 ㈜KT 이동통신 가입자 이동 데이터를 머신러닝으로 학습한 예측치**다. 원문: "㈜케이티의 이동통신 데이터를 기반으로 제공되는 관광지별 조회일 기준 향후 30일간의 관광지 방문자의 집중률 정보". 이는 두 가지 정확도 한계를 내포한다: **(a) 표본 편향** — KT 가입자만 반영, SKT·LG U+ 미포함. **(b) 예측이지 실측이 아님** — 과거 패턴 기반 추정이라 축제·사고 등 돌발 변수에 못 반응. → 화면/서술에서 "실시간 혼잡도"가 아니라 **"예측 혼잡도 지수"로 정확히 명명**해야 한다(designer 03-design-spec.md, content-marketer 05-client-report.md 향후 수정 시 반영).
- **정확도 개선 방향** (통제 불가한 원천 데이터 자체를 바꿀 수는 없으므로): (1) 이미 설계된 tier 배지(실측/추정/데이터없음) 표기를 유지해 과신을 방지 (2) 데이터랩의 다른 지수(관광 수요 강도 등)나 backend Tier C(자체 관측 신호)와 앙상블해 단일 소스 의존도 완화 (3) data.go.kr이 제공하는 **"개방 데이터 활용 매뉴얼 v4.1"** 다운로드 파일에 정확한 필드 정의·갱신 배치 주기가 있음 — API 키 발급 후 첫 확인 작업으로 지정.
- **"갱신주기: 실시간" 표기의 해석 — 확인 필요**: data.go.kr은 이 필드를 "실시간"으로 표기하나, 방법론상 "호출 시점 기준으로 향후 30일 윈도우를 새로 계산해 반환"한다는 뜻일 가능성이 높고, 원본 예측 모델 자체가 초 단위로 갱신된다는 의미는 아닐 수 있다. 정확한 배치 주기는 위 매뉴얼 확인 전까지 단정하지 않는다.
- **여전히 미확인**: 정확한 요청/응답 필드 스펙(Swagger 문서는 API 키 발급 후 열람 가능), 관광지 단위가 숨은길이 다루는 로컬 스팟까지 포괄하는지, 실제 쿼터로 MVP 트래픽을 감당하는지. **backend가 이미 설계한 3-Tier 폴백(Tier A/B/C)은 폐기하지 말고 유지** — 키 발급 후 응답을 실제로 받아봐야 최종 확정된다.
- **여전히 확인 필요**: 나머지 API(두루누비, 소상공인 상권, TourAPI 근처 음식점 등)는 개별 검증 안 됨.

### R2. "AI"의 실체 미정의 — **결정 필요**
- 초안은 Backend를 "Node.js/Express"로, NLP를 "KoNLPy / OpenAI API"로 병기 — **KoNLPy는 Python 라이브러리이므로 Node 스택과 그대로 결합되지 않는다.** 별도 Python NLP 서비스 분리 또는 LLM API 단일화 중 택1 필요.
- "AI 경로 추천"이 **LLM 생성인지, 룰 기반 가중치 스코어링인지** 초안에 정의 없음. 공모전 심사에서 "AI라 부를 근거"를 요구받을 수 있음.
- **완화**: ai-optimization-engineer가 두 안(LLM 기반 / 스코어링 기반 / 하이브리드)의 트레이드오프를 비교하고 1안을 권고한다. 비용 추정 포함.

### R3. EXIF 위치 검증의 신뢰성 — **기술적으로 위험 (N1으로 후순위 처리)**
- EXIF GPS 태그는 **위조가 자명하게 쉽고**, 동시에 **주요 SNS·메신저·iOS 공유 경로에서 자동 제거**된다. 즉 위조는 막지 못하면서 정상 사용자는 인증에 실패하는 최악의 조합이 될 수 있다.
- 브라우저 Geo-location 역시 **개발자도구·가상 위치 앱으로 스푸핑 가능**하며, 웹 환경에서는 네이티브 앱 수준의 무결성 검증 수단이 없다.
- **판단**: 초안의 "인증 완료 시 쿠폰 지급"은 **금전적 가치가 걸린 위조 유인**을 만든다. MVP에서 제외하고, 설계 문서에는 "제한 사항 + 향후 대안(예: 상점 QR, 서버측 IP-지오 교차검증)"만 기술한다.

### R4. 개인정보·위치정보 수집 범위 — **법률 스크리닝 필수**
- 초안이 수집을 전제하는 항목: 자연어 취향 입력(민감 취향 추론 가능), 정밀 위치, 사진(EXIF 포함), 동행자 구성(가족·반려동물·연인 등 **가족관계 추론 가능 정보**).
- **확인 필요**: 위치정보법상 "위치정보사업자/위치기반서비스사업자" 신고 대상 여부 — 단기 1회성 수집이라도 해당될 수 있음.
- **확인 필요**: 자연어 입력을 외부 LLM API로 전송할 경우 **개인정보 국외이전 고지·동의** 요건.
- **완화**: MVP는 **정밀 위치 대신 시/군/구 단위 지역 선택**으로 대체 설계 가능한지 designer/backend가 검토. 4차 게이트에서 legal-counsel 정식 판정.

### R5. 회원가입 전제의 마찰 — **설계 판단 필요**
초안은 온보딩 NLP를 **회원가입 단계**에 배치했다. 공모전 심사위원이 **회원가입 없이 즉시 체험**하지 못하면 완성도 평가에서 불리하다.
- **권고**: 비회원 체험(guest) 경로를 두고, 온보딩 결과를 세션/로컬에 임시 보관하는 방식을 designer + backend가 검토. (PRD 확정 사항 아님 — 부서 검토 후 결정)

### R6. 지도 SDK 및 외부 API 라이선스 — **확인 필요**
- Kakao/NAVER Maps JS SDK의 **무료 쿼터, 공모전/비상업 이용 조건, 로고·저작권 표기 의무** 확인 필요.
- Tmap Route API의 **키 발급 요건과 과금** 확인 필요 (N4로 후순위).
- **완화**: MVP는 지도 SDK 1종만 채택. backend-engineer가 채택안과 근거를 명시.

### R7. 동적 로드밸런싱의 자기모순 — **논리 보강 필요**
초안 4절은 "임계치 초과 시 B/C/D로 분산"이라 했으나 **임계치 수치, 측정 지표(세션? 조회수? 길안내 요청?), 대안 경로가 4개 이상 확보된다는 보장**이 없다. 대안 경로가 부족한 지역에서는 규칙이 작동하지 않는다.
- **완화**: ai-optimization-engineer가 (a) 지표 정의, (b) 임계치 산출 근거, (c) 대안 부족 시 폴백(예: 시간대 분산 추천)을 포함해 설계.

### R8. 공모전 일정 — **확인됨 (2026-07-23, 대표 제공 "공모전 분석" PDF)**
- 접수기간 2026.7.6.~7.21. **접수 완료.** 예비심사·OT 7월 말, 서비스 개발기간 7월 말~9월 말(약 8주), **1차 심사(서면+기능) 10월 중**, 최종 PT 심사 10월 중(1차 상위 3팀), 시상식 11~12월. 상세는 `_공모전분석-대회요강.md` 참고.
- PRD C1(대표 답변 "마감 약 3개월 여유")과 일치 — 모순 아니고 구체화됨.
- **신규 확인 필요 (요강에서 드러난 것)**: (a) 제출물이 "더미데이터 사용 불가·공사 OpenAPI 실제 연동 완료 확인"을 요구함 — 후속 구현 프로젝트는 목업이 아니라 처음부터 실연동으로 설계해야 함. (b) 팀원 전원 콘텐츠랩(`api.visitkorea.or.kr`) 회원가입이 1차 심사 서류 제출 전 필수 — **이건 대표/팀원이 직접 해야 하는 행정 절차**(계정 생성이라 대행 불가).

### R9. 브랜드 표기 불일치 — **경미, 3안으로 늘어남**
- 초안: "SUMUENGIL / SUMUEN", designer 제안: `Sumeungil`(국어 로마자 표기법 일치), 대표 제공 대회 분석 PDF: `SUMGIL`. 세 표기가 다 다르다 — 단, PDF의 `SUMGIL`은 대회 공식 표기가 아니라 분석 문서 작성자의 표기로 보인다.
- **완화**: 여전히 **최종 표기는 대표 결정 사항**(PRD C5 = 08 정본 E6)으로 남긴다.

### R10. 사진/위치 인증(N1) 제외 결정과 대회 요강의 충돌 — **대표 판단 완료 (2026-07-23)**
대회 공식 개발 로드맵 체크리스트(`_공모전분석-대회요강.md` 5.2절)는 **"웹 Geo-location + 사진 인증 모듈 동작 확인"을 명시적 항목**으로 요구한다. 반면 애초 설계 파이프라인(2026-07-22)은 R3 판단에 따라 EXIF/사진 인증(N1)을 완전히 제외했었다.
- **대표 결정**: "대회 공식 개발 체크리스트를 먼저 따라." → 3.2절 R3의 세 가지 선택지 중 **(b) 쿠폰 없이 약한 형태의 사진 인증**으로 확정하고 M8로 승격. R3의 보안 근거(위조 용이성, 금전 유인 결합 시 위조 유인 증가)는 폐기된 게 아니라 **설계 제약으로 흡수**된다 — 인증을 "신뢰도 절대 지표"가 아니라 "보조 신호"로 설계하고, 쿠폰(N2)과 분리해 금전 유인을 제거한다.
- 이 결정은 대회 요강 전체(5.2절 체크리스트)를 스코프의 상위 기준으로 삼는다는 원칙으로 확대 적용되어, N3(오디오가이드)·N4(Tmap)도 함께 MVP(M9·M10)로 승격됐다. 3.2절 참고.
- **후속 조치 필요**: M8이 재도입되면서 07-legal-review.md의 위치정보법·초상권 이슈가 다시 열린다. legal-counsel·security-engineer 재검토 필수 (구현 착수 전이 아니라 **설계 확정 전** 조건으로 격상 — 이미 한 번 제외했다가 되살린 기능이라 더 신중해야 한다).

**병렬 가능 근거**: 3개 부서는 본 PRD의 MVP 정의(M1~M7)를 공통 입력으로 삼으므로 상호 대기 불필요. 단, 아래 인터페이스 3건은 **부서 간 합의가 필요**하므로 각자 자신의 안을 제시하고 planning-lead가 취합 시 조정한다.
- (a) 온보딩 태그 스키마 — AI가 정의, backend가 저장, designer가 입력 UI 표현
- (b) 경로 비교 리포트의 필드 — AI가 산출, designer가 표현, backend가 서빙
- (c) 위치 정밀도 수준 (정밀 좌표 vs 시군구) — R4 관련, 3부서 공통 영향

### 6.3 ai-optimization-engineer 지시서

**목표**: 초안의 "AI"를 **연산 가능한 정의**로 바꾼다. M1(온보딩 NLP), M3(1:1 대조 경로), M6(동적 로드밸런싱) 3개가 핵심.

**산출 파일**: `projects/sumeungil/02-ai-strategy.md`

**읽을 파일 (이것만)**:
- `projects/sumeungil/00-PRD.md` (본 문서)
- `projects/sumeungil/_draft-원본기획서.md` (2.1 페르소나 표, 3.2 온보딩·AI경로, 4절 로드밸런싱)

**작업 항목**:
1. **온보딩 NLP 설계 (M1)** — 자연어 입력 → Intent/Entity 추출 → 태그 집합. **태그 스키마를 명시적으로 정의**(축: 동행/이동수단/분위기/스팟선호/접근성 등). 초안 2.1의 페르소나 3종 입력 예시가 실제로 이 스키마로 변환되는지 워크스루로 검증.
2. **R2 결론** — LLM API 기반 / 룰·키워드 기반 / 하이브리드 3안 비교(정확도·비용·지연·오프라인 시연 가능성). **1안 권고 + 근거.** 공모전 시연 환경에서 외부 API 장애 시 폴백도 포함.
3. **경로 스코어링 알고리즘 (M3)** — 의사코드 수준으로 정의:
   - 입력: 사용자 태그 벡터, 후보 스팟/코스 집합, 혼잡도 지수, 거리/동선
   - 연산: 가중합 스코어링 공식 (가중치가 온보딩 태그에서 어떻게 유도되는지 명시)
   - 출력: 핫플 코스 vs 숨은길 코스 **1:1 비교 리포트 필드 정의** (초안 3.2 표의 4개 행을 실제 산출 가능한 수치로 환산)
4. **동적 로드밸런싱 규칙 (M6, R7)** — 측정 지표 정의, 임계치 산출 근거, 분산 대상 선정 로직, **대안 경로 부족 시 폴백**(예: 시간대 분산).
5. **비용 추정** — LLM 사용 시 온보딩 1건당 예상 토큰/비용, 월간 추정 (가정은 가정이라고 명시).
6. **데이터 흐름 다이어그램** — 온보딩 → 태그 → 가중치 → 랭킹 → 리포트를 1장으로.

**제약**:
- 모델 학습/파인튜닝 제안 금지 — 학습 데이터가 없다. 추론 기반 설계만.
- 공공데이터가 실제로 어떤 필드를 주는지 **가정하지 말 것**. 필요한 필드를 나열하고 "backend 확인 필요"로 넘길 것.
- 정확도 수치를 근거 없이 제시하지 말 것.

```
[다음 부서가 알아야 할 것]
1. 확정한 온보딩 태그 스키마 — backend의 DB 스키마와 designer의 칩(chip) UI가 이것을 그대로 따라야 한다.
2. 1:1 비교 리포트의 출력 필드와 값 범위 — designer가 이 필드만으로 화면을 그린다.
3. LLM 채택 여부 — 채택 시 자연어 입력의 외부 전송이 발생하므로 legal-counsel의 국외이전 검토 대상이 된다.
```

### 7.1 대표 답변 (2026-07-22)

- **C1 — 마감 여유 있음.** 공모전 제출 마감까지 약 3개월 남았다. 8주 로드맵(설계 이후 실제 구현 착수 시)이 시간상 무리 없이 들어간다.
- **C2 — API 키는 관광데이터랩에서 지급 예정.** 아직 발급 전이므로 R1의 실제 호출 검증은 **키 수령 후에나 가능**하다.

R1 참고. 단, 정확한 응답 필드는 API 키 발급 후에만 열람 가능해 **완전히 닫힌 것은 아니다.** → **backend의 3-Tier 폴백 설계는 안전망으로 유지**하되, Tier A가 유력해졌으므로 우선순위는 낮춘다. 참고로 대표가 함께 제공한 `data.go.kr/data/15101914` 링크는 집중률 데이터가 아니라 **관광사진 API**였다(확인 결과 정정).
- **C4 — 구현 아님, 기획서까지.** "아직은 초안이기에 배포 정도의 구현은 아니다"라고 명시했다. → **PRD 4절이 정의한 "최종 결재 대상 = 설계 문서 4종 + 목업 묶음"이 그대로 맞다.** 실제 서비스 구현은 이번 스코프가 아니며, 별도 후속 판단 시점까지 착수하지 않는다.

아래는 설계 편의를 위한 **작업 가정**이며 확정 사실이 아니다. 반증되면 재작업 대상이다.
