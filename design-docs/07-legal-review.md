# 4차 검토 — LLM(Ollama/Qwen2.5) 모델 라이선스 1차 스크리닝 (2026-07-31)

> **배경**: 대표가 "Ollama 모델 상업 사용 가능 여부 + 고지 의무"를 질의했고, 오케스트레이터가 1차 답변(구동 소프트웨어와 모델 가중치 라이선스를 분리해서 봐야 한다는 요지)을 마쳤다. 이 절은 그 1차 답변을 legal-counsel 관점에서 검증·기록하는 것이며, 이번 M-스코프(M8~M10) 게이트 재검토와는 별개의 **오픈소스/모델 라이선스 스크리닝**이다.
> **근거**: 대표·오케스트레이터가 확인한 사실관계(각 라이선스 공개 조건, 오늘 배포 서버 구성 변경 이력)를 재검증하며 기록한다. 벤더별 라이선스 원문 전문을 이 세션에서 재조회하지는 않았으므로, 확실하지 않은 세부 조건은 "확인 필요"로 남긴다.

## 게이트 판정 (본 절 한정)

# **주의** — "위험" 요소는 발견 즉시 제거되어 현재는 해소, 단 고지 체크리스트 1건 남음

오늘 배포 서버에 Qwen2.5-3B(연구용 라이선스)를 일시 사용했던 것은 **그 시점 기준으로는 "위험"에 해당했을 사안**이다(공모전 상금·상용화 전제 서비스에서 비상업 전용 모델을 상업적 맥락에 사용). 다만 라이선스 확인 즉시 제거·교체가 완료되어 **현재 배포 구성 기준으로는 위험 요소가 남아있지 않다.** 남은 것은 한국 AI기본법상 생성형 AI 고지 의무를 상용 런칭 단계에서 문서화(이용약관·서비스 안내)해야 한다는 "주의" 1건뿐이다.

## 1. 구동 소프트웨어(Ollama) — MIT 라이선스

- Ollama 자체(모델을 구동하는 서버 소프트웨어)는 MIT 라이선스로 배포된다. MIT는 카피레프트 조건이 없는 permissive 라이선스로, 소스 재배포 시 저작권 고지 문구만 유지하면 상업적 사용에 제약이 사실상 없는 것으로 통상 알려져 있다.
- 이 프로젝트는 Ollama를 **서버 내부에서 실행만 하고 Ollama 소스 자체를 재배포하지 않는다**(설치형 바이너리를 그대로 사용하는 구조). 소스 재배포가 없으므로 MIT의 저작권 고지 동봉 의무도 사실상 발생하지 않는다.
- **판정: 문제없음.** Ollama 자체는 상업 사용·고지 의무 모두 걸림 없음.

## 2. 모델 가중치(Qwen2.5) — 크기별로 라이선스가 다르다는 점이 핵심

Ollama는 "구동기"일 뿐이고, 실제로 법적 조건을 좌우하는 것은 **그 위에 올리는 모델 가중치의 라이선스**다. Qwen2.5 계열은 크기별로 라이선스가 다르므로 일괄 판정할 수 없다.

| 모델 크기 | 라이선스 | 상업 사용 | 고지 의무 |
|---|---|---|---|
| 0.5B / 1.5B / 7B / 14B / 32B | Apache 2.0 | 가능 | 가중치 자체를 재배포할 때만 라이선스 사본 동봉 의무. **서빙(모델 출력물만 API로 제공)은 재배포가 아니므로 별도 고지 의무가 발생하지 않는 것으로 통상 해석된다** |
| **3B** | **Qwen Research License (연구용)** | **불가** — 상업적 이용 자체가 금지된 라이선스로 통상 알려져 있음 | 해당 없음(애초에 상업 사용이 금지되므로 고지로 해결되는 문제가 아님) |

- **오늘 발생했던 사안**: 응답 성능 문제로 배포 서버에 Qwen2.5-3B를 일시적으로 사용했다. 이는 연구용 라이선스 모델을 상업적 맥락(공모전 출품이 상금·상용화를 전제한다는 점에서 "비상업"으로 보기 어렵다는 판단은 2차 검토 §L-1 계열과 동일한 보수적 관점)에서 서빙한 것이어서, 그 시점 기준으로는 라이선스 저촉 소지가 있는 "위험" 사안이었다.
- **조치 결과**: 라이선스 확인 즉시 해당 모델을 제거했다. 현재 배포 서버는 **1.5B(Apache 2.0) 설치 + LLM 기능 비활성 폴백 모드**로 운영 중이며, 로컬 개발 환경은 **7B(Apache 2.0)**를 사용한다. 즉 현재 시점 기준으로 상업 사용이 금지된 모델은 어떤 환경에서도 구동되고 있지 않다.
- **재발 방지 조치(권고)**: "Qwen Research License(3B류) 연구용 모델"을 이 프로젝트의 **사용 금지 목록**으로 명시 관리할 것을 권고한다 — 향후 성능 튜닝 과정에서 다시 3B를 켜는 판단을 하지 않도록, ai-optimization-engineer/backend-engineer가 모델 후보를 검토할 때 이 표를 참조할 것.
- **판정: 3B 사용 건은 조치 완료로 "위험" 해소, 현재 구성(1.5B 서빙 + 7B 로컬)은 문제없음.**

## 3. 고지 의무 — 라이선스상 의무와 별개로 AI기본법 고지 의무가 있다

- **라이선스 관점**: 위 §1, §2에서 확인했듯 가중치를 재배포하지 않고 서빙만 하는 현재 구조에서는 Apache 2.0/MIT 어느 쪽도 이용자 화면에 별도 고지 문구를 노출할 의무를 발생시키지 않는 것으로 판단한다.
- **국내 규제 관점(별개 사안)**: 한국 AI기본법(2026.1 시행으로 파악)은 생성형 AI를 사용해 산출물을 만들어 제공하는 경우 그 사실을 이용자에게 고지할 의무를 규정하는 것으로 통상 알려져 있다. 이는 모델 라이선스와 무관하게, "생성형 AI를 서비스에 쓴다"는 사실 자체에서 발생하는 별도의 규제 요건이다.
- **현재 이행 상태**: 서비스가 온보딩 답변마다 "숨은길 AI" 라벨과 "AI 답변은 참고용" 문구를 노출하고 있어, **현재 시연/개발 단계 기준으로는 사실상 이행하고 있다고 볼 수 있다.**
- **남은 과제(체크리스트)**: 상용 런칭(공모전 심사 이후 실제 서비스화) 시점에는 화면 라벨만으로는 부족할 수 있고, **이용약관·서비스 안내 문서에 "생성형 AI를 사용해 응답을 생성한다"는 사실을 명시적으로 기재**해야 한다. 정확한 문구 요건(법 조항, 표시 위치·크기 등 세부 기준)은 이 문서만으로 확정할 근거가 없어 **확인 필요로 유지**한다.
- **판정: 주의** — 현재 화면 라벨은 최소 이행 수준으로 인정할 수 있으나, 상용화 단계 전 정식 고지 문구를 이용약관·서비스 안내에 반영하는 것을 체크리스트 항목으로 등록한다.

## 4. 향후 모델 교체 시 주의 — 모델별 고지 조건이 다르다

이번 3B 사안이 보여주듯, LLM 모델은 "무료/오픈소스"라는 표면적 정보만으로 상업 사용 가능 여부·고지 의무를 판단할 수 없고 **모델별·크기별로 라이선스 조건이 다르다.** 향후 모델을 교체(성능/비용 개선 목적)할 경우 아래와 같이 계열별로 조건이 상이하다는 점을 참고해 **교체 전 반드시 legal-counsel 재스크리닝을 거칠 것**을 권고한다.

- **Llama 계열(Meta)**: 커스텀 라이선스로, 상업 사용은 대체로 허용되나 파생물·서비스에 **"Built with Llama" 류의 출처 표기 의무**가 통상 부과되는 것으로 알려져 있다. 월간 활성 사용자 수 기준 조건이 걸리는 버전도 있었던 것으로 알려져 있어 별도 확인 필요.
- **Gemma 계열(Google)**: 자체 이용정책(Gemma Terms of Use / Prohibited Use Policy) 준수 의무가 별도로 부과되는 것으로 알려져 있다 — 라이선스 허용과 별개로 금지 용도 조항 위반 여부를 확인해야 한다.
- **Qwen 계열**: 이번에 확인했듯 **크기(파라미터 수)별로 Apache 2.0과 연구용 라이선스가 혼재**한다 — 모델 카드에서 크기별 라이선스를 개별 확인해야 하며, "Qwen이니까 오픈소스"라고 일반화하면 안 된다.
- **공통 원칙(권고)**: 모델 교체·추가 도입 시 (a) 모델 카드에 명시된 라이선스명 확인, (b) 상업적 사용 허용 여부 확인, (c) 재배포/파생물 배포 시 고지 의무 확인, (d) 서빙(출력물 제공)만 하는 현재 구조에서도 별도 표기 의무가 있는지 확인 — 이 4가지를 backend/ai-optimization-engineer가 모델 후보 비교표에 포함하도록 권고한다.

## 5. 종합 판정 (본 절)

**주의.** "위험" 판정 요소(3B 연구용 라이선스 모델의 상업적 배포)는 오늘 라이선스 확인 즉시 제거·교체 조치로 이미 해소됐고, 현재 배포 구성(1.5B 서빙 + LLM 비활성 폴백, 로컬 개발 7B)은 라이선스 관점에서 문제없음으로 판정한다. 다만 **AI기본법상 생성형 AI 사용 고지를 상용 런칭 전 이용약관·서비스 안내에 정식으로 반영**해야 한다는 점, 그리고 **향후 모델 교체 시 모델별 고지 조건이 다르므로 교체 전 재스크리닝이 필요**하다는 점을 체크리스트로 남긴다.

## 4차 게이트 판정 (최상단, 3차 검토 반영 — 갱신)

# **주의** — "위험" 판정 아님, 단 조건이 있다

M8~M10 재도입으로 "위험(전문가 확인 필요 수준의 명백한 저촉 소지)"으로 격상되는 항목은 **없다.** backend·designer·QA가 R10 제약(보조 신호 한정, 쿠폰 미결합, EXIF 불신)을 설계·문서 수준에서 충실히 흡수했고, 이는 2차 검토가 확립한 최소수집 원칙(좌표 body 전송·원좌표 미저장)과 동일한 계보다.

다만 **한 가지 조건이 이 판정을 지탱한다**: **backend §15.1.4의 EXIF 제거가 현재 "필요 시"(선택)로 남아 있는데, 이것이 "무조건"(강제)으로 바뀌지 않은 채 M8이 실사용자에게 노출되면, 이 판정은 그 시점에 "위험"으로 격상된다.** 이유는 아래 §1에서 직답한다. 즉 지금 이 시점(설계 문서 단계)의 판정은 "주의"이되, **EXIF 전면 제거 강제화가 구현에 실제로 반영되는지가 이 판정의 전제조건**이다.

## 1. SEC→L-D — 사진 EXIF 잔류가 L-1(위치기반서비스사업자 신고) 판정의 전제를 바꾸는가

**결론: 두 가지를 분리해서 답한다. (1) EXIF가 제거되지 않으면 L-1 판정의 전제가 "더 나빠진다" — 새로운 독립적 위험 벡터가 생긴다. (2) EXIF를 제거해도 L-1(신고 대상 여부) 자체는 원래대로 "확인 필요"로 남는다 — EXIF 문제가 사라져도 "브라우저 Geolocation 좌표를 서버가 수신·처리한다"는 사실 자체가 신고 대상 판단 기준일 수 있다는 원래 질문은 그대로 열려 있다.**

- backend는 이미 원좌표(lat/lng)를 DB에 저장하지 않고 `distance_m`만 남기도록 설계했다(`01-backend-design.md` §15.1.2 "왜 원좌표를 저장하지 않나"). 이 설계만 보면 "위치정보를 축적하지 않는다"는 주장이 성립할 여지가 있다.
- 그런데 **사진 파일 자체에 EXIF GPS 태그가 남으면**, backend가 DB 컬럼에서 지운 정밀 좌표가 **오브젝트 스토리지의 사진 안에서 되살아난다.** 이는 `distance_m`만 저장한다는 최소수집 설계와 **완전히 별개의 경로**로 정밀 위치가 보관되는 것이므로, "우리는 좌표를 저장하지 않는다"는 주장의 신뢰성 자체를 무너뜨린다. `06-security-report.md`가 이를 S-H8(High)로 지적하고 "EXIF strip을 '필요 시'가 아니라 '무조건'으로" 요구한 것은 정확한 지적이다.
- **따라서**: EXIF를 저장 전 전면 제거(재인코딩 방식 권장, S-H8 완화책과 동일)하도록 강제하면, 사진을 통한 정밀 위치 잔류라는 **추가 위험 벡터는 닫힌다.** 이 조치가 반영되면 backend의 "원좌표 미저장" 설계 원칙이 사진에도 일관되게 적용되는 것이므로, **이 문서 관점에서는 "문제없음"으로 판정할 수 있는 조건이 충족된다.**
- **그러나 이것이 L-1(위치기반서비스사업자 신고 대상 여부) 자체를 해소하지는 못한다.** L-1은 "정밀 좌표를 서버가 수신해 위치 판정(거리 계산)에 이용하는 행위 자체"가 위치정보법상 위치기반서비스에 해당해 신고 요건을 발생시키는지를 묻는 질문이고, 이는 **저장 여부·EXIF 여부와 무관하게 별개로 남는 질문이다.** M8은 브라우저 Geolocation 좌표를 요청 body로 받아 거리 계산에 **실제로 이용**한다(`01-backend-design.md` §15.1.4 `verify_visit`). "1회성·비저장 처리"가 신고 면제 사유가 되는지는 이 저장소 문서만으로 확정할 근거가 없다 — **확인 필요를 유지한다.**
- **요약**: EXIF 제거를 필수로 강제하면 M8은 "L-1의 전제를 더 나쁘게 만드는 요인"은 제거되지만, **원래 R4/L-1이 갖고 있던 "확인 필요" 상태 그대로로 돌아갈 뿐이며, 그 이상 해소되지는 않는다.** 추측하지 않는다 — 신고 요건의 정확한 적용 범위는 전문가 자문 대상이다.

## 2. SEC→L-E — 방문 인증 사진의 초상권(타인 얼굴 포함 가능성)

**결론: 확인 필요로 유지하되, 현재 설계(비공개 저장·비재배포·7일 TTL)를 조건으로 하면 "주의" 수준으로 관리 가능하다고 판단한다. "위험"으로 볼 근거는 현재 설계상 부족하다.**

- 사진에 촬영자 본인 외 가족·동행자·우연히 찍힌 행인의 얼굴이 담길 가능성은 실제로 있다. 민법상 인격권(초상권)은 본인의 동의 없이 얼굴 등 신체적 특징을 촬영·이용당하지 않을 권리로 통상 알려져 있으며, 이 서비스가 "타인의 얼굴이 찍힌 사진"을 수집·보관하는 구조를 만든다면 리스크 요인이 되는 것은 맞다.
- **다만 리스크의 크기를 좌우하는 요소들을 현재 설계에서 확인하면**:
  - 사진은 **공개적으로 재서빙되지 않는다** — `01-backend-design.md` §15.1.3의 H1~H3 응답 어디에도 photo URL이 없다(`06-security-report.md` S-M11 "사진이 API 응답으로 재서빙되지 않아... 저장형 XSS 실현 경로가 짧다"는 서술과 같은 근거). 즉 서비스가 이 사진을 다른 사용자·검색엔진·SNS에 노출시키는 "공표·이용" 행위를 하지 않는다.
  - 보관 기간이 **7일 TTL**로 제한되고(§15.1.2, 가정값), 만료 시 배치 잡이 파기한다.
  - 단, **버킷 접근 권한(공개/비공개)이 아직 미확정**이다(S-M12) — 만약 버킷이 공개(public-read)로 구성되면 검색엔진 크롤·URL 추측 등으로 사진이 외부에 노출될 실질적 경로가 생기고, 이 경우 초상권 리스크는 "관리 가능한 수준"에서 "실질적 노출 위험"으로 바뀐다.
- **판정**: (a) 비공개 버킷 강제 + 단기 서명 URL(S-M12 완화책 채택), (b) 7일 TTL 파기 유지, (c) EXIF 제거(§1)까지 함께 반영되는 것을 조건으로 하면, 이 문서 수준에서는 **"주의"로 관리 가능**하다고 본다. 이 세 조건 중 하나라도 빠지면 초상권 리스크는 재평가가 필요하다.
- **정확한 법적 해당 여부(예: 초상권 침해 성립 요건, 서비스 운영자의 책임 범위)는 이 문서만으로 확정할 수 없다 — 확인 필요 — 전문가 자문 권장으로 유지한다.**
- **실무 권고 (설계에 즉시 반영 가능한 완화책)**: 캡처 모달의 "왜 필요한가요" 안내(§13.1.1)에 **"본인 위주로 촬영하고, 동의 없이 타인의 얼굴이 크게 나온 사진은 피해 주세요"** 류의 안내 문구를 추가할 것을 권고한다. 이는 법적 의무 이행이 아니라 **사용자 행동을 통한 리스크 저감 조치**이며, 최종 문구는 다른 동의 문구와 함께 전문가 확인 후 확정한다.

## 3. SEC→L-G — M9 오디오 가이드 URL 스트리밍/캐싱 재배포가 원저작권자 이용약관상 허용되는가

**결론: 확인 필요 — 전문가 자문 권장. 단, 현재 설계(바이트 미프록시)는 리스크를 낮추는 방향으로 설계돼 있어 "주의" 수준이며, 향후 설계가 바뀌면(오디오 바이트 자체를 프록시/캐싱) 재평가가 필요하다.**

- `01-backend-design.md` §15.2.2는 명시적으로 "오디오 바이트는 서버가 프록시하지 않는다. 메타데이터 + 원천 스트리밍 URL만 전달하고 재생은 클라이언트가 원천 URL로 직접 한다(대역폭·저작권 재배포 리스크 회피)"고 설계했다. 이는 **우리 서버가 오디오 콘텐츠 자체를 재호스팅·재배포하는 것이 아니라**, 원 제공자(오디/한국관광공사)의 URL을 그대로 클라이언트에 전달하는 구조다.
- Redis 캐싱(§15.2.3)도 **오디오 바이트가 아니라 메타데이터(제목·URL 등)를 3600초 캐시**하는 것이며, 이는 일반적인 API 응답 캐싱에 가깝다.
- 이 구조는 "재배포"라기보다 "링크 전달"에 가까워 저작권법상 노출 정도가 상대적으로 낮다고 볼 여지는 있다. 그러나 **다음은 이 저장소 문서만으로 확정할 수 없다**:
  1. 오디 API(또는 한국관광공사)의 이용약관이 **제3자 앱이 API를 통해 스트리밍 URL을 자사 서비스 UI에 노출·재생시키는 것 자체를 허용하는지** — "메타데이터 재사용"과 "임베드/재생"은 약관상 다르게 취급될 수 있다.
  2. 스트리밍 URL이 **상시 공개 URL인지 서명·만료 URL인지**(backend Q-D13, 미확인) — 서명 URL이라면 재전달·캐싱 자체가 발급 목적을 벗어난 이용일 가능성이 있다.
  3. 상업적 이용(공모전 출품이라도 서비스 형태 운영) 조건.
- **판정**: "확인 필요"로 유지하되, **현재 설계(바이트 미프록시, 메타데이터만 캐시)를 그대로 유지하는 조건**으로 "주의" 수준으로 본다. backend가 향후 오디오 바이트를 직접 프록시·재인코딩·영구 캐시하는 방향으로 바꾸면, 그 시점에는 이 판정을 재검토해야 한다.

## 4. N7 — M8 동의(consent)를 backend가 수신·기록하지 않는 문제

**결론: 법률적으로 문제가 될 소지가 있다고 판단한다. "주의" — 구현 착수 전 반드시 반영해야 하는 항목으로 격상한다.**

- 개인정보(특히 위치·사진처럼 민감할 수 있는 정보)를 처리하는 경우, 처리자가 **적법한 동의를 받았음을 필요시 증명할 수 있어야 한다**는 것이 개인정보 처리의 일반적 실무 원칙으로 통상 알려져 있다. 동의 여부·시점·범위를 서버가 기록해두지 않으면, 이용자가 "동의한 적 없다"고 주장할 경우 이를 반박할 근거가 사업자에게 남지 않는다.
- 현재 설계는 designer(`03-design-spec.md` §13.1.2)가 화면에서 "동의 체크 + 위치확인 + 사진첨부" 3조건을 제출 게이트로 걸어두었지만, backend(`01-backend-design.md` §15.1.3 H1)의 요청 스펙에는 `{place_id, lat, lng}`뿐이고 **동의 여부·시각·문구 버전을 받는 필드가 없다.** 즉 사용자가 화면에서 동의 체크박스를 눌렀다는 사실이 **서버 어디에도 기록되지 않는다.**
- 이는 QA가 이미 N7(Minor)로 지적했고, backend·legal 공동 소관으로 4차 게이트 필수 항목으로 넘겨졌다. legal-counsel 관점에서도 **동일하게 문제로 본다.** Minor라는 QA의 심각도는 "지금 당장 설계 문서 단계에서 게이트를 막을 정도는 아니다"라는 뜻이지, "무시해도 된다"는 뜻이 아니다.
- **조치(구현 착수 전 필수)**: H1 요청/DB 스키마에 최소한 다음을 추가할 것을 권고한다 — 동의 여부(boolean), 동의 시각(timestamp), 동의한 문구의 버전(예: `consent_version` — 문구가 "확정 전 임시"에서 정식본으로 바뀔 것이므로 버전 관리가 필요). 이는 온보딩 국외이전 동의(2차 검토 §1 ②)에서 이미 다룬 것과 같은 성격의 요구사항이며, backend가 별도 설계 없이 해당 패턴을 재사용할 수 있다.

## 5. 대표 판단 완료 사항 재확인 — L-1 자체는 "결정된 사실"이 아니다

PRD R10은 이미 "쿠폰 없이 약한 형태의 사진 인증"으로 대표가 확정했지만, 이는 **스코프(무엇을 만들지)에 대한 대표 결정**이지 **법률 문제(신고 대상 여부 등)를 대표가 판정한 것은 아니다.** 이 재검토 이후에도 L-1(위치기반서비스사업자 신고 대상 여부)은 여전히 미확인이며, 이는 §4(아래 갱신 리스트)의 최우선 항목으로 유지된다.

## 6. 대표가 실사용자 공개(시연 URL 포함) 전에 반드시 해야 할 일 — 우선순위 순 (M8~M10 반영 갱신판, 2차 검토 §4를 대체)

1. **[최우선] 위치기반서비스사업자 신고 대상 여부 확인 (L-1 / Q-L5)** — 온보딩 위치 기능뿐 아니라 M8(방문 인증 Geolocation)도 동일 질문의 적용 대상이다. 방통위 관련 문의 또는 전문가 자문. 미확인 상태로 정밀좌표·M8 인증 기능을 실사용자에게 공개하지 말 것.
2. **[신규 · M8 최우선] 사진 EXIF 전면 제거를 "선택"이 아니라 "무조건 강제"로 구현할 것 (S-H8 / SEC→L-D)** — 저장 전 재인코딩 방식을 권장한다(S-M11 매직바이트 검증까지 동시 해소). **이것이 반영되지 않은 채 M8이 실사용자에게 공개되면, 이 문서의 판정은 "주의"에서 "위험"으로 격상된다.**
3. **[신규 · M8] 사진 오브젝트 스토리지 버킷을 비공개로 강제 + 단기 서명 URL로 확정 (S-M12 / SEC→L-E 전제)** — 공개 버킷으로 방치되면 초상권·EXIF 위험이 실질화된다.
4. **[신규 · M8] backend가 동의(consent) 수신·기록 필드를 API/DB 스펙에 추가 (N7)** — 구현 착수 전 필수. 동의 여부·시각·문구 버전을 함께 기록할 것.
5. **국외이전 고지 문구 확정 + 개인정보처리방침 게시** — 현재 화면 문구는 M8 동의 문구를 포함해 전부 "확정 전 임시"다(총 5곳, §7 참고). 이전받는 자·국가·목적·보유기간을 명시한 정식 문구를 전문가 검수 후 확정하고, 처리방침 문서를 실제로 게시할 것.
6. **[신규 · M8] 방문 인증 사진의 초상권 문제 전문가 확인 (Q-L6 / SEC→L-E)** — 확인 후에도 비공개 저장·미재배포·7일 TTL 설계는 유지할 것.
7. **[신규 · M9] 오디오 가이드 원천 스트리밍 URL의 재전달·임베드가 이용약관상 허용되는지 확인 (Q-D13 / SEC→L-G)** — 상시 URL인지 서명·만료 URL인지 포함.
8. **LLM 벤더의 zero-data-retention(ZDR) 여부 확인** (2차 검토 승계).
9. **`wheelchair_friendly`/`stroller_friendly` 등 접근성 정보의 민감정보 해당 여부 전문가 확인** (2차 검토 승계).
10. **공모전 공모요강 원문에서 저작권/IP 귀속 조항 확인 (L-13)** — 아래 §7에서 상술하듯, 이번 M8~M10 재검토는 대회 요강 §5.1 "이미지, 폰트, API 저작권 및 초상권 문제 사전 점검" 체크리스트 항목에 **직접 대응**하는 작업이다. 이 재검토(SEC→L-D/E/G)가 그 항목의 실질 내용을 채우지만, IP 귀속 조항 자체는 여전히 대표가 요강 원문에서 별도 확인해야 한다.
11. **채택 공공데이터셋별 이용허락 조건, 지도 SDK/Tmap 최신 이용약관 확인** (2차 검토 승계, backend-engineer 소관, Q-M5 포함).
12. **배포 인프라 확인** — Nginx가 실제로 요청 body를 로깅하지 않는지 등 (2차 검토 §3-1 승계).
13. **`src/` 코드 착수 시점에 의존성 파일 확정본으로 오픈소스 라이선스 재확인** (2차 검토 승계).

## 7. M8 동의 문구를 지금 초안으로 제시할 수 있는가

**판정: 아니다. 여전히 "확정 전 임시" 표기를 유지해야 한다.**

- 2차 검토 §3(고지·동의 문구 초안)이 이미 개인정보 수집·이용 동의, 위치정보 수집 동의, 국외이전 고지, 공공데이터 출처 4종의 **참고용 초안**을 제시한 바 있고, 최종 문구는 전문가 검수 후 확정하도록 명시했다. M8 재도입으로 캡처 모달의 `consent-card`(`03-design-spec.md` §13.1.1)가 5번째 "확정 전 임시" 문구 자리가 됐다.
- M8용 동의 문구를 "참고용 초안" 수준으로조차 지금 확정해 제시하지 않는 이유:
  1. **§1(L-D)에서 다룬 대로 EXIF 제거가 아직 설계 문서에서 "필요 시"(선택)로 남아 있다** — 실제로 무엇을 수집·보관하는지(사진 안의 정밀 위치 포함 여부)가 구현 시점에 확정되지 않으면, "무엇에 대해 동의를 구하는지"를 정확히 문구화할 수 없다.
  2. **§2(L-E) 초상권 문제와 §6-3(버킷 ACL)이 아직 미확정**이다 — 동의 문구에 "타인 얼굴 촬영 자제 안내"를 포함할지, 어떤 수준으로 포함할지는 초상권 판정 이후에 정하는 것이 맞다.
  3. **§4(N7) 동의 기록 필드 자체가 API 스펙에 없다** — 무엇을 "동의 기록"으로 남길지 정해지지 않은 상태에서 문구만 먼저 확정하면, 문구와 실제 처리(기록 여부·보관 항목)가 어긋날 위험이 있다.
- **권고**: 2차 검토 §3 초안 4종과 동일한 형식으로, 아래 정보가 확정되는 즉시 M8 문구 초안을 추가한다 — (a) EXIF 강제 제거 여부 확정, (b) 버킷 비공개·TTL 확정, (c) 동의 기록 필드 확정. 그 전까지는 designer가 이미 반영한 "문구 확정 전 임시 — legal-counsel"(`03-design-spec.md` §13.1.1) 표기를 그대로 유지한다.

## 8. 대회 요강 체크리스트 "이미지, 폰트, API 저작권 및 초상권 문제 사전 점검"과의 연결

`_공모전분석-대회요강.md` §5.1은 1차 심사 서류 제출 전 확인해야 할 항목으로 **"이미지, 폰트, API 저작권 및 초상권 문제 사전 점검"**을 명시하고 있다. 이는 단순한 사내 리스크 관리가 아니라 **공모전 제출 요건**이다. 이번 재검토는 이 체크리스트 항목의 실질적 내용을 다음과 같이 채운다.

| 요강 체크리스트 항목 | 대응하는 이번 재검토 항목 | 현재 상태 |
|---|---|---|
| API 저작권 (오디오 가이드) | §3 SEC→L-G / Q-D13 | **확인 필요** — 원천 URL 재전달의 이용약관상 허용 범위 미확인 |
| API 저작권 (Tmap Route) | 2차 검토 승계 L-9/L-10, Q-M5 | **확인 필요** — backend-engineer 소관, 키 발급·과금·이용조건 |
| API 저작권 (지도 SDK, 공공데이터) | 2차 검토 승계 L-9/L-10 | **부분해소** — 출처표기 UI는 신설, 조건 확인은 backend 소관으로 남음 |
| 초상권 (방문 인증 사진) | §2 SEC→L-E / Q-L6 | **확인 필요** — 단, 현재 설계(비공개·미재배포·7일 TTL)를 조건으로 "주의" 관리 가능 |
| 이미지/폰트 저작권 (디자인 에셋) | 이번 재검토 범위 밖 | **미점검** — designer가 실제 채택한 아이콘·폰트·이미지 에셋의 라이선스는 이 문서가 다루지 않았다. `03-design-spec.md`가 폰트/아이콘을 실제로 확정하는 시점에 별도 확인 필요 (신규 항목으로 등록) |

**결론**: 이 재검토(SEC→L-D/E/G, N7)가 요강 §5.1 체크리스트의 "API 저작권 및 초상권" 부분을 실질적으로 다뤘다고 볼 수 있으나, **전부 "확인 필요"가 남아 있는 상태이지 "점검 완료"가 아니다.** 요강 체크리스트를 문자 그대로 충족시키려면 위 표의 "확인 필요" 항목들이 실제로 종결돼야 한다. 또한 "이미지·폰트" 저작권은 이번 재검토가 다루지 않은 새로운 빈틈이므로, designer가 최종 에셋을 확정하는 단계에서 legal-counsel이 재검토해야 할 항목으로 추가한다.

## 9. content-marketer가 반드시 반영해야 할 고지사항 / 사용 금지 표현 (M8~M10 반영 갱신, 2차 검토 §5를 대체)

**고지사항 (반영 필수, 신규)**
- M8 "방문 인증"을 소개할 때, 이것이 **위치 스푸핑을 막지 못하는 보조 신호**이며 **신뢰도 절대 지표가 아니라는 점**을 실제 설계(§15.1.6)와 다르게 축소·과장하지 않는다.
- M9 오디오 가이드를 "우리 서비스가 직접 제공"하는 것처럼 서술하지 않는다 — 실제로는 원 제공자(오디/한국관광공사)의 콘텐츠를 링크로 연결하는 구조다(§3).

**사용 금지 표현 (2차 검토 승계 + 신규)**
- "실방문 인증", "인증 리뷰", "방문 인증 완료(검증됨)" 등 **강한 인증/신뢰를 단정하는 표현** — `08-interface-contract.md` D4 전면 금지 승계 + QA가 재확인(재수록). "약한 현장 신호"라는 설계 실태와 다르게 표현하면 소비자 오인 소지(Q-L7)가 있다.
- "위치 위조 방지", "위조 불가능한 인증" 등 **기술적으로 성립하지 않는 표현** — §15.1.6이 스스로 스푸핑 가능성을 인정한 것과 정면으로 배치된다.
- "사진 속 인물 확인 완료", "초상권 문제없음" 등 **초상권 검토가 끝난 것처럼 단정하는 표현** — L-E가 확인 필요 상태다.
- "오디오 가이드 자체 제작/자체 보유" 등 **콘텐츠 소유·독점 이용권을 시사하는 표현** — 실제로는 원 제공자 URL을 링크하는 구조이며 재배포 허용 여부도 미확인(L-G).
- "개인정보를 전혀 수집하지 않습니다", "완전 비저장", "위치정보를 절대 남기지 않습니다" 등 **절대적·단정적 표현** — 2차 검토와 동일하게 여전히 금지. M8도 사진·거리값을 일정 기간 보관하므로 "완전 비저장"이 아니다.
- "장애인 접근성 인증", "무장애 코스 검증 완료" 등 — 2차 검토 승계, 변경 없음.
- 지도 SDK·공공데이터·Tmap 제공 사업자명을 확정 전 임의로 확정된 것처럼 표기하는 것 — 2차 검토 승계.
- 공모전 수상·심사 결과를 사실인 것처럼 단정하는 표현 — 승계, 변경 없음.

# 2차 검토 (4차 게이트) — 설계 변경 델타 검토

## 4차 게이트 판정 (최상단)

# **주의** — "위험" 판정 아님

**"위험(전문가 확인 필요 수준의 명백한 저촉 소지)"으로 격상되는 항목은 없다.** 1차 검토 대비 설계가 실질적으로 개선되었다. 다만 "확인 필요" 항목 다수가 여전히 남아 있고, 그중 일부는 **실사용자 공개(시연 URL 포함) 전 반드시 종결**되어야 한다. 아래 "대표가 실사용자 공개 전에 반드시 해야 할 일"을 참고할 것.

**요청받은 3건에 대한 결론만 먼저 요약**: (1) 좌표 access log 잔류 문제는 설계상 실질적으로 해소됐다고 판단하나 배포 설정(인프라) 확인이 남아 있다, (2) `wheelchair_friendly`류는 민감정보(건강·장애 관련) 해당 가능성이 높다고 봐야 하며 확인 필요로 유지하되 현재의 비영구저장·세션 한정 설계로 리스크는 크게 낮아졌다, (3) 동의를 자유입력 활성화 이전에 배치한 것은 순서 요건을 충족한다.

| 1 | 위치정보(위치기반서비스사업자 신고 여부) | **부분해소** | access log 잔류로 인한 "비저장 주장 성립 불가" 문제는 ②로 해소. 그러나 **신고 대상 여부 자체(1회성·비저장 수신도 신고 요건에 해당하는지)는 여전히 확인 필요** — 별개 질문이다 |
| 2 | 자연어 온보딩(취향·동행자) 수집 | **전제 변경 (대부분 해소)** | 원문이 저장되지 않으므로 "비정형 텍스트에 아동·제3자 정보가 통제 없이 쌓인다"는 1차 지적의 전제 자체가 사라졌다. 남는 것은 `child_present`/`pet_present` 같은 **구조화 boolean뿐**이며 나이·이름 등 식별정보는 애초에 필드가 없다 |
| 3 | 만 14세 미만 아동 관련 처리 | **전제 변경 (대부분 해소)** | 위와 동일 이유. 아동 본인 가입 구조가 아니라는 전제도 변화 없음. 향후 `raw_input`이 부활하면(대표가 E2를 뒤집는 경우) 재점검 필요 |
| 4 | 최소수집 원칙 / 동의 설계 | **해소** | 개인정보 수집·이용 동의 체크박스(§3.8 (a))가 실제로 화면에 반영됨. 다만 문구는 "확정 전 임시" 상태 — 정식 개인정보처리방침 게시는 별도 과제 |
| 5 | 국외이전(LLM API) | **부분해소** | 고지 UI 신설 + **동의 취득 시점이 자유입력 활성화 이전으로 배치**되어 보안팀 SEC→L-C 우려가 해소됨(§3 참조). 단 (a) 고지 문구의 정확한 법적 요건, (b) 개인정보처리방침에 이전받는 자·국가·목적·보유기간 명시, (c) 벤더 zero-data-retention 계약 여부(E4, 미확인)는 **여전히 확인 필요** |
| 6 | LLM API 이용약관(상업적 이용) | **미해소 (노출면은 축소)** | 호출 지점이 온보딩 1곳으로 고정되어 검토 범위는 좁아졌으나, 약관 확인 자체는 아직 이뤄지지 않았다 |
| 7 | AI 생성물의 권리 귀속 | **리스크 실질 축소** | `build_verdict`가 LLM이 아닌 템플릿 조립으로 바뀌어, 화면에 노출되는 자유 문장(headline)에서 AI 생성물 저작권 이슈가 사실상 사라졌다. 남는 AI 산출물(구조화 태그·점수)은 저작물성이 낮아 이 항목의 실질 노출은 크게 줄었다. "확인 필요" 표기는 유지하되 우선순위는 낮춘다 |
| 8 | 사진 업로드 + EXIF | **문제없음 (유지, 오히려 강화)** | N1 컬럼 자체를 만들지 않는 설계가 그대로 유지됨 |
| 9 | 공공데이터 이용 조건 | **부분해소** | 전역 footer 출처 표기 UI가 신설됨(§3.8 (c)). 데이터셋별 정확한 이용허락 조건 확인은 여전히 backend 소관 확인 필요 |
| 10 | 지도 SDK | **부분해소** | 저작권 표기 자리 신설(§3.8 (d), 사업자 미확정으로 "확인 중" 임시 표기). 최신 무료 티어·상업적 이용 조건 확인은 미해소 |
| 11 | 회원가입(정보통신망법) | **문제없음 (해소 강화)** | 동의 체크박스 UI가 실제로 반영됨 |
| 12 | 소상공인 쿠폰 | **해당 없음 (유지)** | N2 미구현 유지 |
| 13 | 공모전 IP 귀속 | **미해소 (변경 없음)** | 대표가 공모요강 원문을 확인해야 하는 항목. 설계 변경과 무관 |
| 14 | 해외 사용자 / GDPR | **문제없음 (유지)** | 국내 대상 가정 변화 없음 |
| 15 | 오픈소스 라이선스 | **미해소 (변경 없음)** | `src/` 코드 착수 전이라 재확인 대상 자체가 아직 없음 |
| **16 (신규)** | `wheelchair_friendly`/`stroller_friendly` 등 접근성 정보의 민감정보(건강·장애) 해당성 | **신규 판정 (아래 §3-2 참조)** | 1차 판정표에 개별 항목으로 없었던 것을 보안팀(SEC→L-B)이 지적해 신규로 추가 |

## 3. 보안팀 요청 판정 3건에 대한 직답

### 3-1. SEC→L-A — 좌표의 access log 잔류가 L-1 "비저장" 전제를 무너뜨리는가

**결론: body 전환으로 "비저장" 주장의 기술적 전제는 실질적으로 회복됐다고 판단한다. 단, 이것으로 L-1(신고 대상 여부) 자체가 해소되는 것은 아니다 — 두 질문은 별개다.**

- Nginx `combined` 로그 포맷은 요청 라인(`method + URI + protocol`)만 기록하고 **요청 본문(body)은 기본적으로 로깅 대상이 아니다.** `POST /api/v1/places/search`로 전환하고 `01-backend-design.md` §3.1 L3(Nginx `$uri`만 기록, 쿼리스트링 제외)까지 적용하면, 좌표가 URL에 실리지 않으므로 **access log에 좌표+guest_id가 같은 줄로 남는 경로는 구조적으로 제거된다.**
- 추가로 필요한 것: 이건 법률 판단이 아니라 **인프라 구현 확인 사항**이다.
  1. 배포 시 실제 Nginx 설정이 `01-backend-design.md` §3.1 L3(요청 URI만 기록)대로 적용됐는지 확인.
  2. 리버스 프록시·CDN·APM(도입 시) 등 Nginx 외의 계층이 **요청 body를 캡처하는 기능을 켜지 않았는지** 확인(APM 도입 여부는 보안 U6에서 이미 "확인 필요"로 분류됨).
  3. 앱 레벨 미들웨어(`request_log.py`)가 body의 `lat`/`lng`/`near`를 실제로 마스킹하는지(설계상 규정됨, 구현 시 QA 대상).
- **L-1(위치기반서비스사업자 신고 대상 여부)은 이 문제와 별개로 여전히 확인 필요다.** "비저장·1회성 수신"이라도 위치정보를 이용해 서비스를 제공하는 행위 자체가 신고 요건에 해당하는지는 access log 문제와 무관하게 남아 있는 질문이며, 이 문서는 확정 판정을 내릴 근거가 없다.

### 3-2. `wheelchair_friendly`가 전 사용자 프로필에 상시 저장 — 민감정보(건강·장애) 판정

**결론: 민감정보(건강·장애 관련 정보)에 해당할 가능성이 높다고 보고 확인 필요로 유지한다. 다만 재작업으로 리스크는 상당히 완화됐다.**

- 개인정보보호법 체계에서 건강·장애 여부와 관련된 정보는 통상 일반 개인정보보다 엄격한 보호를 받는 범주(민감정보)로 다뤄지는 것으로 알려져 있다. `wheelchair_friendly`(휠체어 접근 필요)·`stroller_friendly`(유모차 접근 필요)는 이용자 또는 동행자의 이동 제약·건강 상태를 직접 시사하는 값이므로, **이 범주에 해당할 개연성이 낮지 않다.** 정확한 해당 여부와 그로 인한 별도 동의 의무는 **전문가 자문 없이 이 문서만으로 확정할 수 없다 — 확인 필요로 유지한다.**
- **재작업으로 리스크가 완화된 지점** (질문에서 알려준 사실 반영):
  - `08-interface-contract.md` §1.5 D1에 따라 `accessibility`는 이제 **"true인 항목만 원소로 담는" 구조**로 바뀌었다. 즉 "언급 없음"과 "false로 확정"이 더 이상 같은 표현으로 저장되지 않는다 — 아무 말도 하지 않은 사용자에게는 값 자체가 생성되지 않는다. 이는 **모든 사용자가 아니라 실제로 해당 정보를 제공(또는 LLM이 추출)한 사용자에게만 값이 생긴다**는 뜻이므로, "전 사용자 프로필에 상시 저장"이라는 전제 자체가 D1 이후로는 정확하지 않을 수 있다. 단, LLM이 문장에서 임의로 추출해 값을 만들 수 있는 구조는 여전히 남아 있어(사용자가 명시적으로 선택하지 않아도 텍스트에서 추론될 수 있음) 민감정보 판정 필요성 자체는 사라지지 않는다.
  - `01-backend-design.md` §10.6 R4 / `08-interface-contract.md` §1.7 E3에 따라 `tag_vector`의 `wheelchair_friendly`·`stroller_friendly` 해당 인덱스는 **DB 저장 시 0으로 마스킹되고, 세션(Redis) 한정으로만 하드필터에 사용**된다. **영구 저장을 하지 않는다는 이 설계는 민감정보 리스크를 크게 낮추는 방향이 맞다** — 개인정보(특히 민감정보)는 보유기간이 짧을수록, 영구 저장이 없을수록 리스크가 낮아진다는 일반 원칙에 부합한다.
  - 보안팀이 제안한 "LLM 추출이 아니라 사용자가 칩으로 직접 선택한 값만 저장"(A1/A2 human-in-the-loop 분리) 원칙이 채택되면 법적 근거가 "추론 수집"에서 "정보주체의 명시적 제공"으로 바뀌어 리스크가 더 낮아진다. 이 원칙이 실제로 반영됐는지는 이 재검토의 확인 범위 밖이므로 backend/AI 문서에서 재확인 필요.
- **종합**: "확인 필요"는 유지하되, 이미 반영된 완화책(true-only 구조 + 비영구저장 + 세션 한정)을 **그대로 유지하는 조건으로 "주의" 수준**으로 본다. 만약 대표가 향후 이 필드를 영구 저장하는 방향으로 되돌리면(08 §1.7 E3의 변경 트리거), 그 시점에는 별도 동의 항목 신설이 사실상 필수가 될 가능성이 높다고 보아야 한다.

### 3-3. SEC→L-C — A1(온보딩 미리보기)이 이미 국외전송이므로 동의가 그 이전이어야 하는가

**결론: 그렇다. 그리고 재작업이 이 요건을 충족했다고 판단한다.**

- "저장하지 않는 미리보기"라도 온보딩 자유 서술이 A1 호출 시점에 이미 외부 LLM 서버로 전송된다면, 국외이전이라는 처리 행위 자체는 저장 여부와 무관하게 그 시점에 발생한 것이다. 따라서 동의는 **전송(=A1 호출) 이전**에 확보돼야 한다는 보안팀 지적은 타당하다.
- `03-design-spec.md` §3.8·§4에 따르면 국외이전 고지 게이트가 **자유 텍스트 입력창(textarea) 활성화보다 먼저** 배치되고, 미동의 시 textarea는 `disabled` 상태를 유지하며 "동의하지 않고 칩으로 선택하기" 경로로 유도된다. QA가 코드 레벨에서 우회 경로 없음을 확인했다고 전달받았다. **이 순서와 강제(동의 없이는 자유입력 자체가 물리적으로 불가능)는 SEC→L-C가 요구한 조건을 충족한다.**
- 남은 확인 필요 사항: 고지 문구 자체가 개인정보보호법상 국외이전 고지 요건(이전받는 자, 이전되는 국가, 이전 항목, 이전 목적, 보유·이용 기간 등으로 통상 알려진 요소들)을 실제로 빠짐없이 담고 있는지는 **정식 문구 확정 시점에 전문가 검수가 필요**하다 — 현재는 "확정 전 임시" 문구이므로 이 시점에는 판정하지 않는다.

## 4. 대표가 실사용자 공개(시연 URL 포함) 전에 반드시 해야 할 일 — 우선순위 순

1. **[최우선] 위치기반서비스사업자 신고 대상 여부 확인 (L-1)** — 방통위 관련 문의 또는 전문가 자문. 미확인 상태로 정밀좌표 opt-in 기능을 실사용자에게 공개하지 말 것. (신고가 필요한데 하지 않은 채 공개하면 이 문서의 유일한 잠재적 "위험" 후보가 된다.)
2. **국외이전 고지 문구 확정 + 개인정보처리방침 게시** — 현재 화면 문구는 전부 "확정 전 임시"다. 이전받는 자·국가·목적·보유기간을 명시한 정식 문구를 전문가 검수 후 확정하고, 처리방침 문서를 실제로 게시할 것 (L-5).
3. **LLM 벤더의 zero-data-retention(ZDR) 여부 확인** (08 §6 E4) — 미확인 상태를 "성과"처럼 서술하지 말 것.
4. **`wheelchair_friendly`/`stroller_friendly` 등 접근성 정보의 민감정보 해당 여부 전문가 확인** — 확인 후에도 현재의 "true 항목만 저장 + 비영구·세션 한정" 설계는 유지할 것(되돌리지 말 것).
5. **공모전 공모요강 원문에서 저작권/IP 귀속 조항 확인** (L-13) — 이 저장소 문서만으로는 확인 불가.
6. **채택 공공데이터셋별 이용허락 조건, 지도 SDK 최신 이용약관 확인** (L-9/L-10) — backend-engineer 소관.
7. **배포 인프라 확인** — Nginx가 실제로 요청 body를 로깅하지 않는지, 프록시/APM 도입 시 body 캡처 기능이 꺼져 있는지 (§3-1 참조, 법률 판단이 아니라 구현 검증).
8. **`src/` 코드 착수 시점에 `package.json`/`requirements.txt` 확정본으로 오픈소스 라이선스 재확인** (L-15).

## 5. content-marketer가 반드시 반영해야 할 고지사항 / 사용 금지 표현

**고지사항 (반영 필수)**
- 랜딩/제안서에 AI(LLM) 처리 및 해외 서버 전송 사실을 숨기거나 축소하지 않는다 — 온보딩 화면에 이미 고지되므로 대외 카피와 일관되게 노출한다.
- 위치정보 기능을 소개할 때 "opt-in", "정밀 좌표 비저장" 등 실제 설계에 맞는 표현만 쓴다.

**사용 금지 표현**
- "실방문 인증", "인증 리뷰", "방문 인증" — `08-interface-contract.md` D4에서 이미 전면 금지 확정. 재확인 차원에서 병기.
- "개인정보를 전혀 수집하지 않습니다", "완전 비저장", "위치정보를 절대 남기지 않습니다" 등 **절대적·단정적 표현** — 실제로는 opt-in 수집·마스킹·세션 한정 저장 구조이지 수집 자체가 0인 것은 아니며, L-1(신고 대상 여부) 등 확인 필요 항목이 아직 남아 있다.

## 2. 부서별 조치 사항

### backend-engineer
- 데이터셋 검증 표(R1 대응)에 **"이용허락 조건/출처표시 의무"** 열 추가.
- 지도 SDK 채택안 확정 시 **무료 쿼터·로고 표시 의무·상업적 이용 제한**을 이용약관 기준으로 명시.
- 위치 정밀도 설계(R4)에서 **시/군/구 단위 선택안을 기본값으로 우선 검토** — 정밀 좌표를 쓸 경우 위치기반서비스사업자 신고 여부 확인 필요 사실을 문서에 명시.
- 온보딩 원문 텍스트 저장 방식(영구 vs 태그 추출 후 폐기)을 DB 스키마 설계에 옵션으로 반영.
- N1(EXIF)·N2(쿠폰)는 이번 설계에서 구현하지 말고 "제한사항" 문단으로만 유지(PRD 지시와 동일).

### ai-optimization-engineer
- R2(LLM vs 룰 기반) 트레이드오프 비교에 **"LLM 채택 시 개인정보 국외이전 고지·동의가 추가로 필요해진다"**는 법률 리스크를 비교 항목에 포함할 것.
- LLM API 채택 시 해당 사업자의 **상업적 이용 약관 조건**을 확인해 문서에 기재.
- 폴백(룰/키워드 기반)을 선택하면 국외이전 이슈 자체가 사라지므로, 이 점을 권고안의 근거 중 하나로 명시 가능.

### designer
- 온보딩 화면에 **개인정보 수집 안내 문구 + 동의 체크박스 영역** 배치(문구 초안은 3절 참조).
- 회원가입 채택 시 **이용약관/개인정보처리방침 동의** UI 요소 반영.
- LLM 채택 시 온보딩 화면에 **국외이전 고지** 영역 확보(문구는 확정 후 노출, 지금은 자리만 표시).
- 지도 SDK 로고/저작권 표시 영역을 지도 화면에 확보.
- 공공데이터 출처 표기 영역(footer 등) 확보.
- N1(사진 인증) UI는 PRD 지시대로 그리지 말 것.

## 5. 종합 판정 (1차 시점)

**주의** — "위험(전문가 확인 필요)"으로 즉시 격상되는 항목은 없으나, 위치정보(L1)와 LLM 국외이전(L2) 2건은 실사용자에게 공개되는 시점(공모전 시연 URL 포함) 이전에 반드시 확인이 완료되어야 하는 항목이다. 설계 단계에서 시/군/구 단위 위치 대체안과 국외이전 고지 UI 자리를 미리 확보해두면 리스크를 낮출 수 있다.
