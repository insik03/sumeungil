## 1. 대회 개요

- 프롬프톤 수상작 기반 지정과제 10개 중 1개를 선택해, **한국관광공사 OpenAPI를 필수 활용**하여 구현·고도화한 관광 서비스를 겨루는 대회.
- 슬로건: "데이터 가치를 넘어, 서비스로 실현하다: 관광데이터 스케일 UP"
- 숨은길은 **지정과제 2번(오버투어리즘 완화)** 을 선택.

## 2. 지정과제 2번 원문 대조 & 해시태그 매핑

**공고문 해결과제**: 유명 관광지 중심의 관광객 쏠림 현상으로 인한 특정 명소의 오버투어리즘(과밀화) 문제

**참고 예시 서비스** (공고문 예시, 참고사항일 뿐): "오버투어리즘 분산 코스 추천 서비스" — 자유여행객 대상, 실시간 데이터 기반 한적한 대안지 매칭.

### 공고문 지정 해시태그 1:1 기능 매핑표

> **중요**: 공고문에 "1차 심사자료 제출 시 해시태그와 연관된 기능 구현 내용에 대해 기능설명서 작성을 요청"한다고 명시됨 — 즉 이 4종 매핑을 별도 문서로 만들어 제출해야 한다.

| 해시태그 | 숨은길 대응 기능 |
|---|---|
| #혼잡도 분석 | DataLab 집중률 예측 API 연동 화면 (PRD M2) |
| #과밀지역 우회 | AI 1:1 대조형 우회 경로 리포트 (PRD M3) |
| #숨은 명소 | 로컬 상권 매핑 카드 / 소상공인 API 연동 (PRD M5) |
| #코스 추천 | 온보딩 NLP 기반 맞춤 경로 추천 (PRD M1) |

**대회 분석 문서의 전략적 조언**: 공고문 예시는 참고사항일 뿐이므로, 기본 요건을 충족하되 우리 서비스만의 독창적 차별점(자연어 온보딩, 동행자별 맞춤, 실방문 인증)을 강조하라고 되어 있다. **단, "실방문 인증"은 이번 설계 파이프라인에서 N1으로 완전히 제외하기로 결정한 항목과 정면으로 배치된다 — 5절 참고.**

## 4. 심사 기준 및 배점

### 예비심사 (서류심사)
Pass/Fail — 결격사유(작성 누락, 중복 신청 등) 검토만.

### 1차 심사 (서면 및 기능심사) — 100점
- 서비스 구현성 (30점): 과제 연계기능 완결성, 구동 안정성, 완성도
- 서비스 기획력 (30점): 타당성, 구체성, 독창성
- 데이터 활용 적절성 (20점): 공사 OpenAPI 활용 필수
- 서비스 발전성 (20점): 지속성, 확장성

> 구현성+기획력이 60점으로 절반 이상. **"아이디어가 좋아도 실제 안정적으로 작동하는 서비스가 없으면 감점이 크다"**는 분석 — 프로토타입 완성이 최우선 과제.

### 최종 PT 심사 (1차 상위 3팀) — 100점
- 서비스 적정성 (30점): 오버투어리즘 문제 정의의 명확성·논리성 (데이터 증명)
- 서비스 완성도 (30점): **시연 시 API 연동 오류 없는 안정적 구동**
- 서비스 실용성 (25점): 페르소나 3종(가족/연인/혼여행)별 실사용 시나리오 시연
- 발표 점수 (15점): 5분 내 문제-해결-차별점-기대효과 압축 스토리라인

대상(1,000만 원)은 웹·앱 개발 부문 상위 5팀 + 구현 부문 상위 3팀 통합 최종심사로 1팀 선발.

### 5.3 ⚠️ 이번 설계 파이프라인의 결정과 정면 충돌하는 항목 2건

1. **사진 인증 모듈** — 대회 공식 로드맵은 "웹 Geo-location + 사진 인증 모듈 동작 확인"을 체크리스트 항목으로 명시한다. 반면 이번 설계 파이프라인(2026-07-22)은 EXIF/사진 인증(N1)을 **완전히 제외**했다 — 위조가 쉽고 정상 사용자만 인증에 실패하는 구조이며, 금전 가치(쿠폰)가 걸리면 위조 유인이 생긴다는 기술·보안 판단이었다(PRD R3, `04-qa-report.md`, `03-design-spec.md`).
   → **대표 판단 필요**: 대회 심사 기준(구현성 30점, 데이터/기능 완결성)에서 "현장 인증 기능"이 언급되므로 완전 제외가 감점 요인이 될 수 있다. 다음 설계 라운드에서 (a) 원안대로 제외하고 다른 차별점으로 보완할지, (b) 쿠폰 등 금전 유인 없이 사진 인증만 약하게 구현할지, (c) 대안 인증(예: 상점 QR, 서버측 IP-지오 교차검증 — PRD R3가 이미 제안한 대안)으로 대체할지 결정이 필요하다.

2. **더미데이터 사용 불가** — 현재 목업(`mockup/index.html`)은 "예시 데이터입니다" 라벨을 붙인 정적 더미 데이터로 구성되어 있다. 이는 **설계 단계 산출물로는 정당했다**(QA가 명시적으로 검증·승인한 부분). 다만 실제 대회 제출물은 공사 OpenAPI 실연동을 요구하고 더미데이터를 금지하므로, **후속 구현 프로젝트는 목업이 아니라 실제 API 연동으로 처음부터 설계**해야 한다는 뜻이다. PRD C2/C3(API 키·데이터 실재성)이 이미 이 필요성을 지적하고 있었다.
