## 1. 요약 (3~5줄)

"숨은길" 초안(공모전 기획서)을 **실행 가능한 설계 문서 + 목업**으로 구체화하는 작업을 마쳤다. 이번 파이프라인이 만든 것은 **배포된 서비스가 아니라 "구현 설계 + 디자인 시안" 묶음**이다 — 브라우저로 열어볼 수 있는 목업 1개(`mockup/index.html`)와 문서 6종이 산출물의 전부다. QA는 재검수에서 Critical 0건으로 3차 게이트를 통과시켰고, 법률팀은 "위험" 판정 없이 4차 게이트를 통과시켰다. **지금 결재해야 하는 것은 "이 설계 묶음을 1안 확정 설계로 승인할지"이며, 승인해도 이는 배포 승인이 아니라 후속 구현 프로젝트 착수 여부를 판단하는 근거가 될 뿐이다.** 대표가 정해야 할 항목(7건)과 구현 착수 전 반드시 닫아야 할 리스크(QA 1건 + 보안 7건 + 법률 3건)가 남아 있으며, 아래 4~6절에 정리했다.

## 4. 초안 대비 이번 파이프라인이 실제로 바꾼 것

초안은 "기획 언어"였고, 이번 단계는 이를 "구현 언어"로 번역하면서 아래 4가지를 결정·수정·제외했다.

### 4.1 기술 스택 정리 — "KoNLPy / OpenAI API" 이중 표기 → LLM 단일화
초안은 자연어 온보딩 NLP를 "KoNLPy / OpenAI API"로 병기했다. KoNLPy는 Python 라이브러리라 초안의 Node.js/Express 백엔드 스택과 그대로 결합되지 않는 문제가 있었다. ai-optimization-engineer가 LLM 기반 / 룰·키워드 기반 / 하이브리드 3안을 비용·정확도·오프라인 시연 가능성 기준으로 비교했고, **strict JSON Schema 강제 방식의 LLM 단일화**로 결론냈다. 단, LLM 장애 시 룰 기반 폴백 경로를 함께 설계했고, 칩(chip) 직접 선택 경로는 애초에 LLM을 호출하지 않도록 분리했다(이 구조가 나중에 법률·보안 검토에서 "동의 안 해도 서비스가 온전히 동작하는 경로"로 재활용됨 — 4.3절 참조).

### 4.2 EXIF 사진 인증 제외 — 있는 것처럼 서술하지 않음
초안의 "현장 사진 인증 + EXIF 위치 검증 + 인증 완료 시 쿠폰 지급"은 이번 설계에서 **완전히 제외**했다. 사유: (1) EXIF GPS는 위조가 쉽고 동시에 주요 SNS/메신저 공유 경로에서 자동 제거돼 정상 사용자만 인증에 실패하는 구조였고, (2) 브라우저 위치는 스푸핑 가능해 신뢰할 수 없으며, (3) 금전적 가치(쿠폰)가 걸리면 위조 유인이 생긴다. backend는 관련 DB 컬럼을 아예 만들지 않았고, designer는 관련 UI를 그리지 않았다. QA가 2차 검수에서 "인증", "실방문 인증" 계열 표현이 산출물 전체에서 0건임을 grep으로 직접 확인했다. **이 기능은 "축소"가 아니라 "제외"다 — 어떤 화면에도, 어떤 API 응답 필드에도 존재하지 않는다.**

### 4.3 초안에 없던 것 중 새로 추가된 것
- **동의 UI 4종** (개인정보 수집 동의 / LLM 국외이전 고지 / 공공데이터 출처 표기 / 지도 SDK 저작권 표기) — 법률·보안 검토 과정에서 필요성이 드러나 추가됐다. 특히 국외이전 동의는 **자유 텍스트 입력창이 활성화되기 전에** 강제로 거치도록 설계했고, 동의하지 않으면 자유 입력 대신 칩(chip) 선택 경로로 안내한다. QA가 목업 코드 수준에서 우회 경로가 없음을 확인했다.
- **혼잡도 3-Tier + 폴백 구조** (실측=A / 통계추정=B / 자체관측추정=C / 데이터없음=none) — 공공데이터가 확보되지 않는 지역·시간대를 대비해 신설했다. "확인 필요"로 남은 R1(집중률 예측 데이터 실재성) 리스크에 대한 실질적 대응책이다.
- **게스트(비회원) 체험 경로** — 초안은 온보딩을 회원가입 뒤에 뒀으나, 심사위원이 가입 없이 즉시 체험할 수 있어야 완성도 평가에 유리하다는 판단으로 추가했다. 잠정 설계는 "서버 Redis 24시간 보관 + 회원가입 시 프로필 승계"다(대표 결정 대기 E1, 5절 참조).
- **온보딩 태그 축(axis) 7종 · 36차원 벡터 체계** — 초안의 페르소나 서술을 실제로 계산 가능한 스코어링 입력으로 변환하기 위해 신설했다. 초안에는 이 수준의 구조가 없었다.

### 4.4 병렬 작업의 부작용과 그 처리
3개 부서(backend/AI/designer)가 PRD를 공통 입력으로 병렬 작업한 결과, 태그 스키마·비교 리포트 필드·로드밸런싱 로직에서 서로 다른 정의를 썼다(예: 같은 이름 `weight_vector`가 부서마다 다른 것을 가리킴). 이는 QA 1차 검수에서 Critical 3건으로 잡혔고, planning-lead가 정본 문서(`08-interface-contract.md`)를 만들어 조정했다. **이 과정 자체가 이번 파이프라인의 실질적 산출물 중 하나다** — 초안 수준에서는 드러나지 않던 "AI가 산출한 값을 backend가 어떻게 저장하고 designer가 어떻게 표현할지"의 구체적 계약이 이번에 처음 만들어졌다.

## 6. 미해결 리스크

**공통 원칙**: 아래 항목은 이번 설계 단계에서 대표의 최종 결재(설계 묶음 승인)를 막을 사유는 아니지만, **후속 구현 프로젝트가 착수되기 전에 반드시 닫아야** 한다. 특히 보안 High 7건은 QA가 명시한 대로 "설계 단계에서 잡지 않으면 나중에 못 잡는" 성격이라 미반영 상태로 코드 작성이 시작되면 그 순간 Critical로 격상 처리하기로 사전 합의돼 있다.

### 6.1 QA Major 1건 — 전광판 응답에 신뢰도(tier) 표기 누락
전광판(홈 화면 TOP10) API 응답 예시에 개별 항목별 신뢰도 등급(tier: 실측/추정/저신뢰추정/데이터없음)이 빠져 있다. 규칙 자체는 문서에 정확히 적혀 있으나 응답 예시가 그 규칙을 반영하지 못했다. **"혼잡도 신뢰등급이 전 화면에 표기된다"는 서술은 지금 시점에는 사실이 아니다** — 비교 화면에는 있지만 전광판에는 없다. **닫아야 할 시점: 구현 착수 전.** 담당은 backend-engineer(응답 예시 수정)와 designer(홈 화면 배지 자리 추가).

### 6.2 보안 High 7건 — 설계 단계 조건부 승인
보안팀은 Critical 0건으로 3차 게이트를 조건부 통과시켰고, High 7건을 "구현 착수 전 반영 조건"으로 넘겼다.

| ID | 요지 | 현재 상태 |
|---|---|---|
| S-H1 | 온보딩 원문(raw_input)이 아동·장애·종교 등 민감정보를 통제 없이 누적 저장할 위험 | backend가 v1.1에서 **컬럼 자체를 제거**했다고 자체 보고. 08 문서도 이를 반영 |
| S-H2 | 정밀 좌표가 URL 쿼리스트링에 실려 Nginx 로그 등에 잔류, "비저장" 설계 주장이 무효화됨 | backend가 v1.1에서 **body 전송 + 로그 마스킹**으로 전환했다고 자체 보고 |
| S-H3 | 캐시 키에 사용자 구분자가 없어 타인의 개인화 결과(반려동물·장애 정보 추론 가능)가 교차 노출될 수 있음 | backend가 v1.1에서 **캐시 키에 프로필 해시 포함**으로 수정했다고 자체 보고 |
| S-H4 | 게스트 식별자가 쿠키·헤더 이중 경로로 설계돼 있어 타인 프로필 탈취 표면을 만듦 | 08 정본이 **헤더 경로 삭제 + 쿠키 단일화**로 확정, QA가 재검수에서 반영 확인 |
| S-H5 | 경로 비교 헤드라인 생성에 쓰인 2차 LLM 호출에 인젝션 방어가 전혀 없음 | 08 정본이 **LLM 호출을 템플릿 조립으로 대체**, QA가 재검수에서 반영 확인 |
| S-H6 | 공공데이터 API 키가 예외 메시지를 통해 DB에 평문으로 적재될 수 있음 | backend가 v1.1에서 **URL 새니타이저 강제**로 대응했다고 자체 보고 |
| S-H7 | 혼잡도·로드밸런싱 카운터가 무인증 트래픽 기반이라 외부에서 조작(경쟁 관광지 밀어내기 등)이 가능함 | 08 정본이 **주체 단위 dedupe + 이상탐지**로 확정, QA가 재검수에서 반영 확인 |

**중요한 단서**: S-H4·S-H5·S-H7 3건은 QA가 08 정본과 대조해 본문 수준으로 재검증했다. 반면 **S-H1·S-H2·S-H3·S-H6 4건은 backend가 v1.1에서 대응했다고 스스로 보고했을 뿐, QA나 보안팀이 재검증한 기록은 없다.** 대표 결재 전에 이 4건에 대한 재검수 1회를 권고한다. **닫아야 할 시점: 구현 착수 전 (S-H1/S-H2/S-H3/S-H6은 재검증까지 포함해서).**

### 6.3 법률 미해소 3건 — 실사용자 공개(시연 URL 포함) 전 필수
법률팀은 "위험" 판정 없이 4차 게이트를 통과시켰으나, 아래 3건은 실사용자에게 공개하는 시점(공모전 시연 URL 포함) 이전에 반드시 확인이 끝나야 한다고 명시했다. 법률팀 우선순위 그대로 가져왔다.

1. **[최우선] 위치기반서비스사업자 신고 대상 여부** — 정밀 좌표를 opt-in으로 쓰는 것이 위치정보법상 신고 요건에 해당하는지 미확인 상태다. 방통위 문의 또는 전문가 자문이 필요하며, 미확인 상태로 정밀좌표 기능을 실사용자에게 공개해서는 안 된다.
2. **국외이전(LLM 전송) 고지 문구 확정 + 개인정보처리방침 게시** — 현재 화면 문구는 전부 "확정 전 임시"다. 이전받는 자·국가·목적·보유기간을 명시한 정식 문구를 전문가 검수 후 확정해야 한다.
3. **LLM 벤더의 ZDR(zero-data-retention) 계약 여부 확인** — 미확인 상태를 성과처럼 서술하지 말 것(법률팀이 직접 경고한 항목이며, 5절 D9와 동일 사안).

**닫아야 할 시점: 시연 URL 등 실사용자 공개 이전 (구현 착수보다도 앞선 시점일 수 있음).**

## 7. 다음 단계 제안

실제 구현으로 넘어가는 것을 대표가 승인한다면(5절 D4), 아래 순서를 권고한다. 이번 파이프라인의 결과물을 그대로 활용하는 순서다.

1. **6.3절 법률 3건 중 1번(위치기반서비스사업자 신고 여부)을 가장 먼저 확인한다.** 결과에 따라 위치 정밀도 설계(정밀 좌표 vs 시/군/구 단위) 자체가 바뀔 수 있어, 뒤로 미루면 이미 만든 설계를 되돌려야 할 수 있다.
2. **6.1·6.2절의 QA/보안 미해소 항목을 구현 착수 직전에 일괄 재검수 1회로 닫는다.** 특히 backend가 자체 보고만 한 보안 4건(S-H1/S-H2/S-H3/S-H6)의 실제 반영 여부를 QA가 본문 대조로 확인해야 한다.
3. **5절 D2·D3(공공데이터 API 실재성)을 실제로 검증한다.** 지금까지는 문서 기반 설계이며 실제 API 호출 테스트는 0건이다. 이 확인 없이 구현에 들어가면 M2·M3 핵심 기능이 착수 후에야 막힐 위험이 있다.
4. 위 3가지가 정리된 뒤 후속 구현 프로젝트를 `/new-client-project`로 새로 열어, 이번 설계 문서 4종(`00`~`03`) + `08` 정본을 입력으로 backend/AI/designer에 구현 착수 지시를 내린다.
